多智能体同场对话：双通道架构与消息原子落库

2026-10-04GoAI编程

单智能体聊多了不够用，产品要让多个 AI 角色同场对话：用户一句下去，可能好几个角色接话。这套 AI 多智能体对话系统是我在 Lunetale 上做的，要稳住四件事：SSE 和 WebSocket 怎么分工、多角色编排怎么拼上下文、积分怎么扣才不发生「扣了钱却没生成」，以及消息怎么做到不丢不重。这篇把最容易出资金事故的扣费链路讲透。流式那一半的细节见SSE 与上下文压缩。

双通道：一条管流，一条管场

逐字生成是高频、单向、只给发起方的；角色入场、轮到谁说话是低频、要广播全场的。拆成两条通道反而清晰：

SSE 通道WebSocket 通道
方向服务端单向推双向
典型事件delta / done 逐字流角色入场、轮到发言、心跳
受众当前发起请求的用户整个房间在线成员
 
func (s *Service) Push(sessionID string, event Event) {
    if event.Stream { // 逐字生成走 SSE，只推给发起方
        s.sse.PushTo(sessionID, event)
    } else {         // 房间状态走 WS，广播给全场
        s.ws.Broadcast(sessionID, event)
    }
}

一条消息的完整链路：冻结、生成、实扣

早期我图省事：进请求先扣费、再生成。结果 LLM 一失败或超时，钱扣了回复没出来，用户立刻投诉。改成两阶段后整条链路是这样：

用户发消息
   |
   | 0. 幂等查询：重放则直接返回已存消息
   | 1. 冻结占额 freeze(user, cost, ttl=60s)
   v
[路由选模型] -> [LLM 流式生成] --SSE delta--> 用户逐字看
   |                              |
   | 生成成功                      | 失败 / 超时
   v                              v
[事务: 实扣 + 落 user + 落 ai]   [解冻返还 / outbox 补偿任务]
   |
   v
提交，冻结额度真正消耗掉

第一步：冻结占额，不真正扣减

冻结把额度从「可用」挪到「冻结」，用户看到的可用余额变少了，但钱还没真正花掉。用条件更新兜住余额不足：

func (s *Service) Freeze(ctx context.Context, userID uint, cost int) error {
    res := s.db.Model(&Account{}).
        Where("user_id = ? AND points - frozen >= ?", userID, cost).
        Update("frozen", gorm.Expr("frozen + ?", cost))
    if res.RowsAffected == 0 {
        return errInsufficientPoints
    }
    // 记一笔冻结单，带 60s TTL，兜底扫描靠它回收
    return s.db.Create(&Freeze{UserID: userID, Amount: cost,
        Status: "frozen", ExpireAt: time.Now().Add(60 * time.Second)}).Error
}

第二步：成功后在同一事务里实扣并落库

流式全部生成完、确认有交付了，才在一个事务里做三件事：把冻结真正转成扣减、落用户消息、落 AI 回复。要么都成要么都回滚：

func (s *Service) Commit(ctx context.Context, in SendInput, aiReply string) error {
    return s.db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Model(&Account{}).Where("user_id = ?", in.UserID).
            Updates(map[string]interface{}{
                "points": gorm.Expr("points - ?", in.Cost),
                "frozen": gorm.Expr("frozen - ?", in.Cost),
            }).Error; err != nil {
            return err
        }
        if err := tx.Create(&Message{SessionID: in.SessionID, Role: "user",
            Content: in.Content, IdempotencyKey: in.IdempotencyKey}).Error; err != nil {
            return err
        }
        return tx.Create(&Message{SessionID: in.SessionID, Role: "assistant",
            Content: aiReply, Actor: in.Model}).Error
    })
}

失败补偿：解冻与兜底扫描

生成失败或流式超时，直接解冻把额度退回去。万一进程在冻结后、解冻前崩了，冻结单会一直挂着——所以有个定时任务扫过期冻结单兜底返还：

func (s *Service) Release(userID uint, cost int) error {
    return s.db.Model(&Account{}).Where("user_id = ?", userID).
        Update("frozen", gorm.Expr("frozen - ?", cost)).Error
}

// 定时兜底：超过 TTL 仍 frozen 的单子，判失败并返还
func (s *Service) SweepExpiredFreezes() {
    var fs []Freeze
    s.db.Where("status = ? AND expire_at < ?", "frozen", time.Now()).Find(&fs)
    for _, f := range fs {
        s.Release(f.UserID, f.Amount)
        s.db.Model(&f).Update("status", "released")
    }
}

多智能体编排：公共上下文与私有记忆

同场多个角色，prompt 不能每个都塞全量历史。我们把上下文分两层：世界观和公共剧情全场共享，每个角色的私人记忆只拼给它自己。下一个发言者由 director 角色或规则轮次决定：

func BuildPrompt(room Room, speaker string) []llm.Message {
    sys := "世界观：" + room.WorldView + "\n"
    sys += "你扮演：" + room.Characters[speaker].Persona + "\n"
    sys += "公共剧情摘要：" + room.SharedPlot + "\n"
    sys += "你的私人记忆：" + room.Characters[speaker].PrivateMem // 只给发言者
    msgs := []llm.Message{{Role: "system", Content: sys}}
    for _, m := range room.Recent { // 最近对白按序可见
        msgs = append(msgs, llm.Message{Role: m.Role, Content: m.Text})
    }
    return msgs
}

下一个谁说话：默认按角色列表轮转；用户 @ 某个角色则它优先；需要自然接话时，把最近对白喂给一个裁判模型选「谁接最顺」。多角色回复按发言顺序逐条落库，actor 字段记是哪个模型生成的。

幂等：重复请求直接返回已存消息

网络重试、用户手抖，都会让同一条请求进来两遍。带幂等键先查库，命中就直接返回，绝不再走生成：

func (s *Service) ReplayOrCreate(in SendInput) (*Message, bool, error) {
    var exist Message
    err := s.db.Where("idempotency_key = ?", in.IdempotencyKey).First(&exist).Error
    if err == nil {
        return &exist, true, nil // 重复请求：返回已存消息，不再扣费生成
    }
    return nil, false, nil // 首次：继续走 冻结->生成->实扣
}

备选方案：预扣 vs 后扣 vs 冻结两阶段

  • 先扣后生成：实现最简单，但 LLM 失败就是净亏损，用户投诉；
  • 先生成后扣：体验最好，但用户可以故意断连逃单，平台坏账；
  • 冻结两阶段：先冻后扣、失败解冻、定时兜底，资金安全和体验折中，我们选它。

冻结 TTL 设 60 秒：覆盖一次流式生成的正常时长，又不至于让崩溃后冻结额度被占太久。相关的队列兜底与支付履约，可参见分布式锁与支付履约两篇。

核心经验：双通道让流式与房间各走各的路，冻结两阶段让「扣钱」和「交付」对齐。多智能体要稳，关键不是模型多强，而是钱和消息这两条线——先冻结、成功才实扣、失败解冻加定时兜底，幂等键保证重复请求只返回不重复生成；旁路的语音转写与翻译宁可降级也不拖垮主链路。
