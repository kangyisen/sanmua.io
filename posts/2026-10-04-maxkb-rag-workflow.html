MaxKB RAG 实战：从文档解析到溯源兜底的工作流

2026-10-04AIRAG编程

企业里搭问答系统，最朴素的想法是把文档一股脑塞进上下文让大模型答，很快就撞墙：太长塞不下、答得没出处、问不到私有知识时它还硬编。这个企业知识库智能问答项目我基于 MaxKB 搭 RAG，拆成「离线准备」和「在线问答」两半，用工作流把「意图识别 → 检索 → 生成 → 溯源 → 兜底」串起来。这篇按节点讲清楚每步干什么、Agent 何时该去调工具。多步 Agent 编排另见多智能体对话。

整条在线工作流

用户提问
   |
   v
 [意图识别] --+-- 闲聊/通用 --> 直接生成
              +-- 需私有知识 --> [检索] 向量+BM25 -> rerank
              +-- 需实时/结构化数据 --> [Agent 工具节点]
   |                                   |
   v                                   v
 [检索为空/低置信] --> [兜底] 转人工/明说不知道
   |
   v
 [生成] 仅依据上下文，带引用
   |
   v
 [溯源] 返回出处片段 + 文档定位

离线侧：先按结构切，定长滑窗只做兜底

分段策略上我修正了一个常见误区：不是一上来就按固定字符数硬切。正确顺序是先按标题/段落边界切，只有当某段本身超长时，才在这段内部用滑窗兜底。硬切会把一个表格或一个完整论证拦腰切断：

import re

def split_structured(text, max_len=500, overlap=80):
    # 1. 先按标题/段落边界切成结构块
    blocks = re.split(r"\n(?=#{1,6}\s)", text)   # 按 Markdown 标题切
    chunks = []
    for b in blocks:
        b = b.strip()
        if not b:
            continue
        # 2. 短块直接保留；超长块才滑窗兜底
        if len(b) <= max_len:
            chunks.append(b)
        else:
            start = 0
            while start < len(b):
                end = start + max_len
                chunks.append(b[start:end])
                start = end - overlap     # 相邻重叠，防关键句落在切点
    return chunks

默认 max_len=500、overlap=80（字符，示例值）。每块连同文档名、章节路径、原文偏移区间一起向量化入库——这些定位元信息是后面溯源能落地的前提。

在线侧：先做意图识别，别急着检索

不是每个问题都要翻知识库。「你好」「帮我写个周报」这类闲聊去检索只会引入噪声。第一个节点就是分流：

def classify_intent(question):
    if looks_like_internal_factual(question):
        return "retrieval"      # 查私有知识
    if needs_realtime_or_structured(question):
        return "tool"          # 走工具节点
    return "chat"              # 直接生成

分流决定后面走哪条支路：闲聊直接生成、知识问题走检索、需要实时或结构化数据的走工具。

检索：向量 + BM25 混合召回，再 rerank

纯向量检索对「语义近但词面不搭」有效，却容易漏掉精确的专有名词、编号；纯 BM25（关键词）相反。所以我做混合召回：向量和 BM25 各召一批（示例 topK=5），合并后用 rerank 模型重排，取最贴题的几块：

def hybrid_retrieve(question, top_k=5):
    vec_hits = vector_search(question, top_k)     # 语义召回
    bm25_hits = bm25_search(question, top_k)      # 关键词召回
    merged = dedup(vec_hits + bm25_hits)
    reranked = rerank_model.rerank(question, merged)
    return reranked[:top_k]                       # 重排后取前 top_k

拼进生成上下文时，每块都带上出处标记，溯源才能指回去。

生成侧 prompt：必须「有据才答，无据明说」

生成节点最关键的是 prompt 把口径卡死——只许依据上下文答，答不出就明说，不许编：

GEN_PROMPT = """
你是企业知识助手。严格按以下规则作答：
1. 仅依据【参考资料】回答用户问题；
2. 若参考资料中没有相关内容，直接回复「知识库中暂未找到该内容，建议转人工咨询」，不要编造；
3. 回答末尾用 [1][2] 标注引用了哪些资料片段。

【参考资料】
{context}

【问题】{question}
"""

这样输出不是凭空生成，而是检索材料的重组，且每句都能指回某块原文。前端再把对应的文档名、章节、命中片段一起返回。

兜底：低置信就别硬答

检索回来的块要么相似度普遍很低、要么一条都没命中，这时最危险的就是模型硬编。我加了兜底分支先看检索质量：

def should_fallback(hits, min_score=0.5):
    if not hits:
        return True                       # 一条都没召回到
    if max(h.score for h in hits) < min_score:
        return True                       # 最相关的也不够像
    return False

命中兜底时不硬生成知识型答案，明确回复找不到并引导转人工。承认不知道，比答错了可信得多。

Agent 工具节点：私有知识之外该调什么

纯 RAG 只答「躺在文档里的静态知识」。用户问「这个月订单量多少」「某工单状态」，这些知识库不存实时数据——这就是工具节点接管的时机。在 MaxKB 里给它配一个 Function schema，声明能调什么工具、要什么参数：

tools = [{
    "type": "function",
    "function": {
        "name": "query_order_status",
        "description": "根据订单号查询实时订单状态",
        "parameters": {
            "type": "object",
            "properties": {
                "order_id": {"type": "string", "description": "订单编号"}
            },
            "required": ["order_id"]
        }
    }
}]

工具返回的结构化结果再回填进生成上下文，让模型基于「文档片段 + 工具结果」组织最终回答。这背后就是 Function Call 的思路：模型负责推理和组织语言，工具负责它自己拿不到的实时与结构化数据；这条问答 Agent 还接到网页、内部 IM 等多渠道，后端一套编排复用。

怎么评估这套 RAG 有没有变好

不做评估的 RAG 是在裸奔。我的做法是先人工标注一批「问题 + 标准答案 + 应命中的文档」测试问答集，每次改分段或换模型都回归跑一遍，盯三个指标：

  • 召回命中率：该命中的文档有没有真的被召回到；
  • 答案忠实度（faithfulness）：生成的答案是否都能在上下文里找到依据，有没有脱离材料瞎编；
  • 兜底是否生效：对知识库里没有的问题，是不是老实说不知道。

备选方案与权衡

  • 切分：定长 vs 结构化：定长实现简单但会切断语义；结构化更准但要吃文档格式。我选「结构化优先、超长滑窗兜底」；
  • 检索：向量 vs BM25 vs 混合：向量擅长语义、BM25 擅长精确词，混合 + rerank 最稳但成本更高；
  • 工具调用：Function Call vs MCP：Function Call 是当下主流、接一个工具配一个 schema；MCP 是更标准化的工具接入协议，工具多了之后更省心。当前我用 Function Call，MCP 作为下一步演进方向。

核心经验：RAG 的价值不在「让大模型答得更溜」，而在「让它答得有据、且知道自己什么时候答不了」。离线把解析、结构化分段、定位元信息做扎实，在线用意图识别分流、混合检索+rerank 喂上下文、用 prompt 约束有据才答、用溯源钉回原文、用兜底拦幻觉、用标注集回归——整条工作流加起来，才是企业敢真正用起来的问答 Agent。
