MaxKB RAG 实战：从文档解析到溯源兜底的工作流

2026-10-04AIRAG编程

企业里搭问答系统，最朴素的想法是把文档一股脑塞进上下文让大模型答。很快就会撞墙：文档太长塞不下、答得没出处、问不到私有知识时它还硬编。这个企业知识库智能问答项目我基于 MaxKB 搭 RAG，把流程拆成「离线准备」和「在线问答」两半，再用工作流把「意图识别 → 检索 → 生成 → 溯源 → 兜底」串起来。这篇按节点讲清楚每一步在干什么、Agent 什么时候该去调工具。

离线侧：解析、分段、向量化

RAG 的效果上限在入库时就定了大半。离线这条管线分三步：先把 PDF / Word / Markdown 等不同格式解析成纯文本，再分段，最后向量化入库。分段策略不是切得越碎越好：

  • 按结构切：优先顺着标题、段落、列表边界切，别把一个表格拦腰切断；
  • 控制长度：单块太长召回不准，太短上下文不完整；
  • 留重叠：相邻块保留一小段重叠，避免关键句正好落在切点上被割裂。
def split_text(text, chunk_size=500, overlap=80):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap   # 回退 overlap，形成相邻重叠
    return chunks

每一段连同它来自哪个文档、第几节这些元信息一起向量化存进向量库。元信息很关键——后面溯源全靠它把答案指回原文位置。

在线侧：先做意图识别，别急着检索

不是每个问题都需要翻知识库。「你好」「帮我写个周报」这类闲聊或通用任务，去检索反而是噪声。所以工作流第一个节点是意图识别：判断这句话到底是要查私有知识，还是可以直接答，或者该走外部工具。MaxKB 里这是一个分类节点，背后也是调一次模型打标签：

def classify_intent(question):
    # 返回：retrieval / chat / tool
    if looks_like_factual_about_internal(question):
        return "retrieval"
    if needs_realtime_or_structured(question):
        return "tool"
    return "chat"

这一步分流决定了后面走哪条支路：闲聊直接生成、知识问题走检索、需要实时或结构化数据的走工具节点。省掉无谓检索，也避免把闲聊硬凑上一段文档。

检索：召回之后再重排

被判定为知识问题后，把问题向量化去向量库召回 Top-K 相关块。光靠向量相似度还不够——语义近但不是最相关的块容易混进来，所以在召回之上再加一层重排，把真正贴题的几块顶到前面。拼进生成上下文时，我把命中的原文片段连同来源标题一起带上：

def build_context(retrieved_chunks):
    parts = []
    for ch in retrieved_chunks:
        # 每块都标注出处，供后面溯源使用
        parts.append(f"[来源: {ch.doc_title} {ch.section}]\n{ch.text}")
    return "\n\n".join(parts)

上下文里保留出处标记，是「溯源」能落地的前提——生成阶段让模型只依据这段上下文答，就注定它说的每句话都能指回某块原文。

生成与溯源：答案必须能指回原文

生成节点把「问题 + 带出处的上下文」交给模型，约束它只能基于给定材料回答。这样输出不是凭空生成的，而是检索材料的重组。企业场景里「能不能溯源」几乎是刚需——答得对不对先放一边，至少要让人知道这句话是从哪份文档哪一段来的。

关键是入库时就要把定位信息一起存好，别等生成完再回头找。我给每块切片都记下三样东西：文档名、所属章节、以及它在原文里的偏移区间。这样生成侧返回答案时，就能把「结论」和「它来自第几份文档、哪一节、大致哪一段」打包给前端，用户点开能直接定位到原文位置：

  • 文档名：告诉用户答案出自哪份制度 / 手册；
  • 章节路径：比单给一个文件名更好定位，用户顺着目录就能找到上下文；
  • 命中片段：把最相关的那一句原文高亮返回，而不是只甩一个链接。

三段信息里，章节路径和命中片段是「被生产环境教出来的细节」——早期只回文档名，用户点开还得自己翻半天找那句话，溯源就形同虚设；把命中片段直接贴出来，用户一眼就能判断答案靠不靠谱。

兜底：检索为空或低置信时，别硬答

这是「被生产环境教出来的细节」：检索回来的块要么相似度普遍很低，要么一条都没命中，这时候最危险的就是模型一本正经地编一个答案。我在工作流里加了兜底分支——先看检索质量：

def should_fallback(retrieved_chunks, min_score=0.5):
    if not retrieved_chunks:
        return True                      # 一条都没召回到
    if max(c.score for c in retrieved_chunks) < min_score:
        return True                      # 最相关的也不够像
    return False

命中兜底时不硬生成知识型答案，而是明确回复「知识库中暂未找到相关内容」，并引导转人工或建议补充文档。承认不知道，比答错了可信得多，尤其在内部审批、制度这类场景。

Agent 节点：什么时候该去调工具

纯 RAG 只回答「已经躺在文档里的静态知识」。但用户会问「我们这个月的订单量是多少」「帮我查一下某个工单状态」——这些私有知识里没有实时数据。这就是 Agent 节点接管的时机：当意图识别判断需要实时信息、或需要结构化数据时，不去检索文档，而是调用搜索 / API / 数据库工具，拿到结果再交给生成。

问题类型走哪条路原因
制度、手册类静态知识检索 + 生成 + 溯源答案已在文档里
闲聊、通用写作直接生成无需私有知识
实时、结构化数据Agent 调 API / 数据库知识库不存动态数据
私有知识缺失兜底 + 引导宁可说不知道

这背后的判断逻辑，本质上就是理解 Function Call / MCP 的那套思路：模型负责推理和组织语言，工具负责它自己拿不到的实时与结构化数据。最后这条问答 Agent 还接到了多渠道——网页、内部 IM 都能接入同一个工作流，后端一套编排复用。

核心经验：RAG 的价值不在「让大模型答得更溜」，而在「让它答得有据、且知道自己什么时候答不了」。离线把解析、分段、元信息做扎实，在线用意图识别分流、用检索+重排喂上下文、用溯源把答案钉回原文、用兜底拦住幻觉——这一整条工作流加起来，才是一个企业敢真正用起来的问答 Agent。
