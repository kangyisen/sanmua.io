自研 SSRF 防护层：把 URL 抓取关进笼子

2026-10-04Python安全编程

采集器天生就是 SSRF 重灾区：要抓的 URL 一部分来自配置，一部分来自页面里爬出来的链接，等于让程序去访问"别人给的、不完全可信"的地址。一个被污染的链接就能让服务器去请求 127.0.0.1、内网服务，甚至云元数据接口。我没有直接套现成库，而是自己写了一层校验。这篇讲这几道闸分别挡什么。并发模型见asyncio 两级并发那篇，任务可靠性见outbox 与看门狗那篇。

校验流水线：一张流程图

每个 URL 都要跑完下面整条流水线，任何一关不过就拒：

 raw_url
   |-- scheme in {http, https} ?                 否则拒
   |-- 无 userinfo (user:pass@host) ?            否则拒
   |-- host 归一: 整数IP / v4-mapped-v6 / IDNA
   |-- getaddrinfo -> 任一 IP 落入私网/环回/链路本地/元数据?  有则拒
   |-- 端口 in {80, 443} ?                        否则拒
   |-- 锁定已校验 IP 直连 (HTTPS 带 SNI=域名)
   +-- 收到 3xx -> Location 重跑以上全部, 最多 5 跳

第一关：协议白名单 + 剥离 userinfo

file:///etc/passwd、gopher:// 这类协议直接拒。另外要注意 http://user:pass@evil.com@127.0.0.1/ 这种 userinfo 写法，肉眼和某些解析器都会被带偏，我直接拒绝任何带用户名密码的 URL：

from urllib.parse import urlparse

ALLOWED_SCHEMES = ("http", "https")

def safe_url(raw: str) -> str:
    u = urlparse(raw)
    if u.scheme not in ALLOWED_SCHEMES:
        raise ValueError(f"非法协议: {u.scheme}")
    if not u.hostname:
        raise ValueError("缺少主机名")
    if u.username or u.password:
        raise ValueError("URL 携带 userinfo，拒绝")   # user:pass@host 常用于绕过
    return raw

第二关：host 归一，专治各种 IP 伪装

直接拿 ipaddress.ip_address(host) 会漏三种常见绕过。其一，2130706433 这种十进制整数 IP，它其实就是 127.0.0.1；其二，[::ffff:127.0.0.1] 这种 IPv4-mapped IPv6，必须还原成 v4 再判；其三，IDNA/punycode 域名靠 getaddrinfo 正常解析即可。归一函数统一处理前两种：

import ipaddress

def normalize_ip(host: str):
    # 1) 十进制整数 IP，如 2130706433 == 127.0.0.1
    if host.isdigit():
        try:
            return ipaddress.ip_address(int(host))
        except ValueError:
            pass
    ip = ipaddress.ip_address(host)
    # 2) IPv4-mapped IPv6，如 ::ffff:127.0.0.1 还原成 v4
    mapped = getattr(ip, "ipv4_mapped", None)
    return mapped if mapped is not None else ip

def is_public(host: str) -> bool:
    ip = normalize_ip(host)
    return not (ip.is_private or ip.is_loopback
                or ip.is_link_local or ip.is_multicast or ip.is_reserved)

解析时我用 socket.getaddrinfo 取全部 A/AAAA 结果，只要任意一个 IP 落进危险段就整请求拒绝——攻击者可能同时解析出一个公网 IP 和一个内网 IP，只验第一个就被绕过。

第三关：锁 IP 直连，HTTPS 要带 SNI

这一处修过一个真 bug：最早我一律用 HTTPConnection(locked_ip)，结果 HTTPS 站点全部握手失败——因为证书签给的是域名，直接对 IP 建 TLS 连接，证书校验对不上。正确做法是：连接打到已校验的 IP 上，但 TLS 的 SNI 和证书校验仍用原始域名。HTTP 走 HTTPConnection，HTTPS 走 HTTPSConnection 并传 server_hostname：

import ssl, http.client

def open_locked(url: str, locked_ip: str):
    u = urlparse(url)
    if u.scheme == "https":
        ctx = ssl.create_default_context()          # 默认校验证书链
        conn = http.client.HTTPSConnection(
            locked_ip, timeout=5, context=ctx,
            server_hostname=u.hostname)             # SNI/证书按域名，连接按 IP
    else:
        conn = http.client.HTTPConnection(locked_ip, timeout=5)
    conn.request("GET", u.path or "/", headers={"Host": u.hostname})
    return conn.getresponse()

核心还是那句：校验用的 IP 和实际连接的 IP 必须是同一个，中间不给 DNS 任何"变脸"（DNS rebinding）的机会，同时用 server_hostname 保住 HTTPS 的证书校验。

第四关：手动重定向，每跳都重新过闸

千万别用客户端库默认的自动重定向——它会跳过我们的校验。我禁用自动跳转，自己读 3xx、用 urljoin 补全相对路径，对每个 Location 从头跑一遍校验，并限死最多 5 跳：

from urllib.parse import urljoin
MAX_HOPS = 5

def fetch(url: str):
    for _ in range(MAX_HOPS):
        ips = resolve_public_ips(url)          # 解析 + 全量 IP 公网校验
        locked = ips[0]
        resp = open_locked(url, locked)
        if resp.status not in (301, 302, 303, 307, 308):
            return resp
        loc = resp.getheader("Location")
        if not loc:
            return resp
        url = urljoin(url, loc)                 # 相对路径补全
        safe_url(url)                          # 新 Location 重新过全套闸
    raise ValueError("重定向超过 5 跳")

端口白名单与云元数据

传输层再补一刀：只允许 80/443，不允许打 22、6379、3306 这类内网服务端口。云元数据地址 169.254.169.254 属于链路本地段，is_link_local 已能挡，但我仍把它列成显式黑名单单独再拦一次——它是 SSRF 窃取临时凭证的头号目标，宁可重复也不能漏：

ALLOWED_PORTS = {80, 443}
METADATA = {"169.254.169.254"}

def check_port_and_meta(u) -> None:
    port = u.port or (443 if u.scheme == "https" else 80)
    if port not in ALLOWED_PORTS:
        raise ValueError(f"禁止端口 {port}")
    for ip in resolve_public_ips(u.hostname):
        if ip in METADATA:
            raise ValueError("命中云元数据地址")

备选方案与权衡

我的选择备选取舍
自研逐层校验套现成 SSRF 防护库现成库省心但黑盒、版本更新可能漏新绕过手法；自研可控、能针对整数IP/IPv6映射这些边角显式兜底，代价是要自己维护
应用层校验 + 锁 IP统一走正向代理白名单出口代理白名单在网络层更彻底（连被漏判的也出不去），但要多维护一个代理；单进程小体量下应用层校验足够，可作为纵深防御叠加
解析后锁定 IP 直连信任 DNS、交给连接库信任 DNS 就给了 rebinding 可乘之机；锁 IP 虽牺牲了一点连接复用，但换来了一致性

核心经验：SSRF 防护没有"一次校验就万事大吉"，它是一串必须层层独立成立的闸门。协议、userinfo、IP 伪装归一、公网归属、DNS 一致性、每一跳重定向、元数据与端口——任何一层偷懒前面全白费。HTTPS 锁 IP 时别忘带 SNI，否则安全做到了、请求却连不通。把 URL 抓取关进笼子，就是让它无论如何都跑不出你画好的那个公网白名单。
