自研 SSRF 防护层：把 URL 抓取关进笼子

2026-10-04Python安全编程

采集器天生就是 SSRF 的重灾区：我们要抓的 URL 一部分来自配置，一部分来自页面里爬出来的链接，等于让程序去访问"别人给的、不完全可信"的地址。如果不做防护，一个被污染的链接就能让我这台服务器去请求 127.0.0.1、内网服务，甚至云厂商的元数据接口。我没有直接套现成库，而是自己写了一层校验，把 URL 抓取一层层关进笼子。这篇讲这几道闸分别挡什么。

第一关：协议白名单，非 http/https 一律拒

SSRF 最经典的入口就是协议。file:///etc/passwd、gopher://、dict:// 这些根本不该出现在一次网页抓取里。所以拿到 URL 第一件事是解析它，只放行 http 和 https：

from urllib.parse import urlparse

def safe_url(raw: str) -> str:
    u = urlparse(raw)
    if u.scheme not in ("http", "https"):
        raise ValueError(f"非法协议: {u.scheme}")
    if not u.hostname:
        raise ValueError("缺少主机名")
    return raw

别小看这一关，它直接挡掉了用 file:// 读本地文件、用 gopher:// 打内网端口的一大类玩法。

第二关：解析出 IP，内网/环回/保留地址全拉黑

协议合法不代表地址安全。http://127.0.0.1:6379、http://192.168.x.x 都是合法的 http，但指向的是本机和内网。我用标准库 ipaddress 把域名解析成 IP 后，逐个判断它是不是环回、私网、链路本地或保留地址：

import ipaddress, socket

def is_public_ip(ip_str: str) -> bool:
    ip = ipaddress.ip_address(ip_str)
    return not (
        ip.is_private        # 10/8、172.16/12、192.168/16 等私网
        or ip.is_loopback    # 127.0.0.0/8、::1
        or ip.is_link_local  # 169.254.0.0/16
        or ip.is_multicast
        or ip.is_reserved
    )

def resolve_all(hostname: str):
    infos = socket.getaddrinfo(hostname, None)
    return {info[4][0] for info in infos}   # 一个域名可能解析出多个 IP

注意我取的是全部解析结果，不是只拿第一个——攻击者可能让域名同时解析出一个公网 IP 和一个内网 IP，只校验第一个就被绕过了。只要任意一个 IP 落在危险段，整个请求直接拒掉。

第三关：防 DNS rebinding——校验完 IP 就锁死它

这里有个非常隐蔽的坑，叫 DNS rebinding。你校验的时候域名解析成公网 IP，放行；可等真正发起连接时，DNS 又被解析成了内网 IP——两次解析结果不一样，校验形同虚设。堵法是：校验通过后，直接拿那个已经验证过的 IP 去连，同时把原始域名放进 Host 头，让服务器仍能正确路由，而不是再给它一次重新解析的机会：

def guarded_get(url: str):
    u = urlparse(safe_url(url))
    ips = [ip for ip in resolve_all(u.hostname) if is_public_ip(ip)]
    if not ips:
        raise ValueError("解析结果全部落在内网/保留段")
    locked_ip = ips[0]                    # 锁定这个已校验的 IP
    conn = http.client.HTTPConnection(locked_ip, timeout=5)
    conn.request("GET", u.path or "/", headers={"Host": u.hostname})
    # 后续连接都打在 locked_ip 上，不再二次 DNS 解析

核心就一句：校验用的 IP 和实际连接的 IP 必须是同一个，中间不给 DNS 任何"变脸"的机会。

第四关：重定向的每个 Location 都要重新过闸

很多人只校验了最初那个 URL，却忘了跟随重定向。攻击者完全可以让一个合法公网 URL 返回 302，跳到 http://169.254.169.254。所以我的策略是：每一跳重定向都把新的 Location 当成一个全新 URL，从头跑一遍上面所有校验，而不是"第一个 URL 安全，后面一路绿灯"。

  • 不使用客户端库默认的自动重定向，改为自己读 3xx 响应、手动处理 Location；
  • 对每个 Location 重新做协议白名单 + IP 校验 + 锁定 IP；
  • 同时限制重定向跳数（比如最多 5 跳），防止被无限重定向拖死。

别漏了云元数据地址 169.254.169.254

这是最该单独拎出来说的一个地址。云上实例的元数据接口固定监听在 169.254.169.254，它属于链路本地段，上面的 is_link_local 判断理论上已经能挡住。但我还是把它列成一条显式黑名单，单独再拦一次——因为它是 SSRF 打穿云主机、窃取临时凭证的头号目标。宁可重复拦，也不能因为哪天 ipaddress 的判定口径变了而漏过去。

最后一道闸：超时与端口限制

校验都过了，还要在传输层兜底。我对所有抓取请求统一设了连接与读取超时，避免一个慢请求把协程挂死；同时只允许访问标准的 80/443 端口，不允许打 22、6379、3306 这类内网服务端口。这样即便前面某层校验被绕过，攻击者也很难借我的服务器去探测内网的具体服务。

攻击手法靠哪一层挡
file:// / gopher:// 等协议协议白名单，只放 http/https
直接写内网 / 环回 IP解析 IP 后用 ipaddress 拉黑私网段
DNS rebinding 二次变脸校验后锁定 IP 直连，不再二次解析
302 跳转到内网每个 Location 重新校验 + 限跳数
打云元数据 / 内网端口显式黑名单 + 端口白名单 + 超时

核心经验：SSRF 防护没有"一次校验就万事大吉"，它是一串必须层层独立成立的闸门。协议、IP 归属、DNS 一致性、每一跳重定向、元数据地址、超时端口——任何一层偷懒，前面所有努力都白费。把 URL 抓取关进笼子的意思，就是让它无论如何都跑不出你画好的那个公网白名单。
