本地模型调度与云端故障转接

2026-10-13GoAI架构

背景：云端生图不是永远可靠

「一秒修图」（部署包名 aizaotu）的出图链路一开始全部跑在云厂商 API 上：阿里百炼的 qwen-image、腾讯混元的 hy-image-v3.5-preview、阶跃星辰的 step-image-edit-2。这些接口按量计费，公网一抖动、限流一触发（429）或返回 5xx，用户那边就是一张图都出不来。于是我们把 Qwen 图像模型部署进自己的 GPU 机器，通过内网穿透暴露成两个站点（d103、fip），让它在「能力匹配」时优先承接流量，云端则退居故障兜底。

相关代码都在 server/service/business/toolbox/ 下：drawing_local_scheduler.go（站点调度）、drawing_local_task.go（任务协议）、drawing_local_generation.go（生成主链路）、drawing_local_failover.go（转接判定与熔断），配置长在 business.local-model 这一节：

# config.yaml
business:
  local-model:
    primarySite: "d103"
    generationTimeoutSeconds: 180
    pollIntervalMillis: 2000
    fallbackEnabled: true
    sites:
      fip: "https://fip.cpolar.top"
      d103: "https://d103.cpolar.top"

为什么要本地兜底，而不是直接换云厂商

本地 GPU 的边际成本几乎为零，但它的能力是云端的子集：本地是图生图异步任务协议，文生图「协议未指定」直接拒收；最多 3 张参考图；尺寸要求 256–1536、32 像素对齐、总面积不超过 1536x1024。localCapabilityReason 就是这道门槛的实现：

func localCapabilityReason(in modelImageInput) string {
    if len(in.Images) == 0 {
        return "local text-to-image protocol not specified"
    }
    if len(in.Images) > 3 {
        return "local supports at most 3 reference images"
    }
    // 尺寸：宽高 256–1536、均为 32 的倍数、宽*高 <= 1536*1024
    return ""
}

这个设计决定了整个架构的走向：本地不是「更好的云」，而是一个有明确能力边界的廉价通道。能力不匹配时绝不动用本地的熔断状态，直接走云端——否则「本地不支持文生图」会被误判成「本地服务挂了」，白白打开熔断。

真实实现：站点登记与轻量调度器

DrawingLocalModel 持有配置、混元备用配置、一个老路径用的熔断器和一个全局共享的站点调度器（sharedLocalSites）。调度器本身很轻：每个站点一个 localSiteState，记录正在飞的请求数、故障冷却截止时间、半开探测标记和版本号：

type localSiteState struct {
    active       int
    blockedUntil time.Time
    probe        bool
    epoch        uint64
}

// reserve 在网络 I/O 之前预约一个站点：选 in-flight 最少者，并列按 sequence 轮转；
// 健康站点容量打满时在 changed channel 上等待，而不是立刻故障转移。
func (p *localSiteScheduler) reserve(ctx context.Context, sites map[string]string,
    preferred string, excluded map[string]bool, limit int) (*localSiteLease, error)

预约到的 *localSiteLease 在请求结束时 release(failed, cooldown)：失败就把站点打入冷却（默认 30 秒），成功且冷却已过则解封；sync.Once 保证一次预约只释放一次，防止重复减计数：

func (l *localSiteLease) release(failed bool, cooldown time.Duration) {
    l.once.Do(func() {
        s := l.pool.states[l.key]
        s.active--
        if failed {
            if cooldown <= 0 { cooldown = 30 * time.Second }
            s.epoch++
            s.blockedUntil = time.Now().Add(cooldown)
        }
        l.pool.signal() // 唤醒在 changed 上等待的预约者
    })
}

调度主循环 generateScheduledLocal 的关键纪律写在注释里：只有提交前的失败才允许换站点（把该站点加入 excluded 重试）；一旦任务已经 POST 出去（trace.submissionStarted == true），歧义失败直接上抛，绝不拿着同一个 job id 去另一台机器上轮询——那会造成重复扣费和跨站轮询。

任务协议：异步队列与状态机

本地模型是异步任务协议：POST 接单，轮询取结果。任务结构体 LocalModelTask 严格遵循对方的 qwen_query_task.py 语义——任务归创建它的站点所有，换站 404 不能触发重投：

type LocalModelTask struct {
    Site       string                 `json:"site"`
    JobID      string                 `json:"job_id"`
    HTTPStatus int                    `json:"http_status"`
    Status     string                 `json:"status"`
    URL        string                 `json:"url,omitempty"`
    Body       map[string]interface{} `json:"body,omitempty"`
}
// GET /api/jobs/{id}：只查询、不创建；状态机 queued / running / failed / cancelled / completed

一次完整生图在 generateLocalAt 里是固定三步：先 GET /api/health（2 秒超时）确认站点就绪，再 POST /api/jobs 提交任务（期望 202 Accepted，从 body 里取 id），最后按 pollIntervalMillis（默认 2000ms）轮询直到终态：

switch state {
case "queued":
    continue                       // 仍在本地 GPU 队列里
case "running":
    if runningAt.IsZero() { runningAt = time.Now() }
    continue
case "completed":
    // 校验图片 URL 必须是 https，否则视为协议异常
    return drawingResponse{Images: []string{image}}, nil
case "failed", "cancelled":
    return drawingResponse{}, localResponseError(500, body, nil)
}

整个生成被包在 GenerationTimeoutSeconds（默认 180 秒）的 child context 里；超时退出时错误信息特意写明「已提交本地任务等待超时，任务可能继续运行」——因为服务端任务可能还活着，这个信息会参与后面的转接判定，避免误转。

云端故障转接：什么算「可转接」的失败

主入口 GenerateContext 的分支逻辑很清晰：FallbackEnabled 关闭时能力不符直接报错；能力不符（比如 5 张参考图）直接调 backup，即腾讯混元 generateHunyuan（hy-image-v3.5-preview）；否则先打本地，失败且可转接才转云端，并在日志里打 model_fallback from=local to=hunyuan。

「可转接」的判定是整个设计最讲究的部分——localFailureCanTransfer 区分了「服务挂了」和「请求被拒」：

func localFailureCanTransfer(err error) bool {
    if err == nil || errors.Is(err, context.Canceled) { return false }
    var ve *vendorError
    if errors.As(err, &ve) {
        // 内容安全 / 用户输入 / 鉴权类拒绝不是可用性故障，即使被代理包成 5xx 也不转接
        if meta, ok := matchByKeyword(ve.raw); ok &&
            (meta.category == enums.ErrorCategoryContentRisk ||
             meta.category == enums.ErrorCategoryUserInput ||
             meta.category == enums.ErrorCategoryVendorAuth) {
            return false
        }
        return ve.httpStatus == 408 || ve.httpStatus == 429 ||
            ve.httpStatus >= 500 && ve.httpStatus <= 599
    }
    return errors.Is(err, ErrLocalModelUnavailable) ||
        errors.Is(err, context.DeadlineExceeded)
}

老路径上还有一个全局熔断器 localModelFailover：acquire / finish 一对，失败进入 30 秒冷却，冷却后用 probe 半开探测试探一次，epoch 版本号防止「上一代请求的迟到结果」误关新熔断。它的 run 对每个 provider 最多调用一次，计费与审计刻意留在函数外面——同步熔断器绝不和一笔未完成的账单赛跑。

参数差异与离线模板迁移

同一个修图模板，走百炼云端和走本地，参数长得完全不一样：云端 qwen-image 是 messages 风格，参考图是 content 块里的 {image: url}，prepareQwenImageParams 还要把 {image: [url, url]} 数组展开成每张图一个块；本地 /api/jobs 则是平铺的 image_urls / prompt / seed / width / height，没有 messages、没有 cfg_scale、没有 steps。

存量数据库里有一批渠道为阶跃（ai_model 12/13）的老模板，迁移由 scripts/migrate_stepfun_templates_local_qwen.py 这个离线脚本完成，而不是运行时临时改写：

OLD_MODEL = 'step-image-edit-2'
NEW_MODEL = 'local-qwen'   # 后端适配器标签，不是上游模型版本
LEGACY_CHANNELS = (12, 13)
LOCAL_CHANNEL = 15
REMOVED_KEYS = ('cfg_scale', 'steps')  # 本地适配器早已忽略这两个字段

# 改 b_toolbox.ai_model 12/13 -> 15；box_params / params 中
# model -> local-qwen，URI_PATH -> /api/jobs，删掉 cfg_scale/steps。
# 默认 dry-run；--apply 必须提供计划 sha256 与备份目录，
# FOR UPDATE 行锁 + 每 100 条 CASE 批量更新 + ROW_COUNT 逐行校验 + 生成 rollback.sql。

配套的 TestLocalQwenTemplateMigrationPreservesInput 守住了一条底线：迁移前后 normalizeLocalInput 的输出必须 reflect.DeepEqual，且发往上游的 payload 里绝不泄漏 model / URI_PATH / cfg_scale / steps 这些「给人看的标签」。也就是说，数据库里的显示标签和真正发往 GPU 的请求是完全解耦的——标签随便改，实际入参一毫米都不能动。

运维侧还有一个独立入口 cmd/local_model/main.go，支持 health / query / generate 三种模式，可以脱离主服务单独巡检站点、追单个 job id 或手动跑一次完整链路。

取舍小结

  • 能力边界先于故障判断：不支持的请求直接走云端，不碰本地熔断，避免误判。
  • 异步任务只投一次：202 之后绝不重复提交、绝不跨站轮询，歧义失败宁可上抛也不重复扣费。
  • 两层保护：站点级冷却（blockedUntil）管「哪台机器歇一会」，全局熔断器管「整条本地通道歇多久」，半开探测自动恢复。
  • 迁移离线化：DB 脚本 + 等价性测试，标签与请求解耦，可 dry-run、可回滚。

兜底系统最难的从来不是「挂了之后切过去」，而是冷静地区分：这是服务真挂了、请求本就不被支持、还是一笔已经投出去的账单。本地 GPU 调度器用站点冷却、熔断器和只投一次的异步协议，把这三件事拆开记账——便宜的算力才能真正变成用户手里稳出的图。
