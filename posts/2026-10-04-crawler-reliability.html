采集可靠性：outbox、崩溃恢复、优雅停机与看门狗

2026-10-04Python编程

这个采集平台最终是用 Docker / systemd 部署在一台 Linux 机器上长跑的。长跑的进程我早就不指望它不挂了——OOM、发版重启、宿主机维护、甚至掉电，都会发生。真正的问题不是"会不会崩"，而是"崩了能不能自己爬起来、并且一条任务都不丢、也不重复抓一堆"。这篇讲我用 SQLite outbox、崩溃恢复、优雅停机，再加 Redis 去重和 Lua 看门狗，把这套可靠性兜起来的过程。

为什么要 outbox：先落库，再干活

最开始任务只活在内存队列里，进程一死，队列里所有待抓 URL 全部蒸发。我的改造思路很朴素：凡是要做的事，先写进本地 SQLite，再去做。SQLite 单文件、随进程、不用额外依赖，正好当本地 outbox。任务从 outbox 里领走、处理完再更新状态，这样即使处理到一半进程崩了，记录还在磁盘上。

CREATE TABLE IF NOT EXISTS outbox (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    url         TEXT NOT NULL,
    source      TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending',  -- pending/processing/done/dead
    fail_count  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

def enqueue(db, url, source):
    db.execute(
        "INSERT INTO outbox(url, source, status, created_at, updated_at) "
        "VALUES(?, ?, 'pending', datetime('now'), datetime('now'))",
        (url, source),
    )
    db.commit()

崩溃恢复：启动时把没做完的任务捞回来

进程正常退出时任务会走到 done，但崩溃时那些标记成 processing 的任务其实没人做完——它们是上次死掉的 worker 留下的残骸。所以启动第一件事，就是把这些"卡在 processing"的任务重置回 pending，让它们重新被调度：

def recover_stale(db):
    # 上次崩溃时正在处理、却没人收尾的任务，全部退回待处理
    cur = db.execute(
        "UPDATE outbox SET status='pending', updated_at=datetime('now') "
        "WHERE status='processing'"
    )
    db.commit()
    return cur.rowcount   # 启动日志里打一行，能直观看到恢复了多少条

配合前面那篇讲的队列，恢复流程就是：启动 → recover_stale() 把遗留任务翻出来 → 再 SELECT ... WHERE status='pending' 灌回内存队列。不需要人工干预，systemd 一拉起就自动续上。

优雅停机：收到 SIGTERM 后的四步

Docker 停容器、systemd 停服务，发的都是 SIGTERM。如果进程不管三七二十一直接退出，在途任务又会变成上面那种残骸。部署在 Linux 上，我用 asyncio 的信号处理做优雅停机，分四步走：

  • 收到 SIGTERM / SIGINT，置一个停止标志位；
  • 停止取新任务：生产者不再往队列里塞新 URL；
  • 等待在途任务收尾：await queue.join()，让正在抓的请求自然跑完并落库；
  • 最后把 outbox 的缓冲 commit / flush 干净再退出。
async def shutdown(loop, sig):
    stopping.set()                 # 通知生产者停止取新任务
    await queue.join()             # 等在途任务跑完、状态落库
    db.commit()                    # 最后再 flush 一次
    loop.stop()

loop = asyncio.get_running_loop()
for sig in (signal.SIGTERM, signal.SIGINT):
    loop.add_signal_handler(sig, lambda s=sig: asyncio.create_task(shutdown(loop, s)))

这样停机窗口里的任务要么正常做完，要么停在 pending 等下次恢复，绝不会停在半中间的 processing。

Redis 去重：别把同一篇文章抓两遍

6 个数据源里有交叉转载，同一篇资讯可能从两个源都冒出来。抓取前我先问 Redis：这条 URL 的指纹见没见过？用 SET NX，写进去成功才抓，已经存在就直接跳过：

def already_seen(r, url):
    # NX：key 不存在才写入；返回 None 说明之前见过，直接跳过
    ok = r.set(f"seen:{hashlib.sha1(url.encode()).hexdigest()}",
               1, nx=True, ex=7 * 24 * 3600)
    return ok is None

key 带了过期时间，去重集合不会无限膨胀。量大之后可以再上布隆过滤器省内存，但当前量级用一个带 TTL 的 SET 就够了。

Lua 看门狗：超时没 ack 就重放

优雅停机覆盖了"主动退出"，但覆盖不了"worker 卡死"——比如某个请求挂住、协程既不报错也不返回。任务标记成了 processing，却永远等不到它收尾。我的解法是看门狗：worker 领任务时在 Redis 写一个带 TTL 的心跳 key，处理过程中定期刷新；处理完删除并 ack。一个独立的清扫协程定期检查，发现任务还在 processing、但心跳 key 已经没了，就认定这个 worker 死了，把任务重放回 pending。

"判断心跳是否存在 + 失败计数 + 决定是否重放"这几步必须原子，否则两个清扫协程会同时重放同一条任务，所以用 Lua 脚本一次做完：

watchdog = r.register_script("""
-- KEYS[1]=任务心跳 key  KEYS[2]=失败计数 key
-- ARGV[1]=失败阈值
if redis.call("pttl", KEYS[1]) < 0 then        -- 心跳没了，worker 已死
    local n = redis.call("incr", KEYS[2])
    redis.call("expire", KEYS[2], 86400)
    if n >= tonumber(ARGV[1]) then
        return "dead"                            -- 连续失败太多，熔断，别再重放
    end
    return "requeue"                             -- 正常重放一次
end
return "alive"                                   -- 心跳还在，worker 活着，别动它
""")

清扫协程拿到 requeue 就把 outbox 里这条任务改回 pending；拿到 dead 就标记成死信，交给人工或日志排查，不让一条坏任务无限重放、把系统和对端站点都拖死。

可靠性是一层叠一层的，没有银弹

风险靠什么兜
进程崩溃丢任务SQLite outbox 先落库，启动时恢复 processing
发版/停容器丢在途任务捕获 SIGTERM，停取新任务、等在途收尾再退出
重复抓取同一篇Redis SET NX 指纹去重
worker 卡死无人收尾心跳 + Lua 看门狗重放，连续失败熔断

核心经验：可靠性的本质是"任何时刻进程突然死掉，系统都能从磁盘上的状态自愈"。outbox 让任务不丢，优雅停机让在途任务不被腰斩，看门狗让卡死的任务不被遗忘，熔断让坏任务不无限重试。四件事叠起来，才敢把它交给 systemd 长跑。
