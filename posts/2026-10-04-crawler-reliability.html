采集可靠性：outbox、崩溃恢复、优雅停机与看门狗

2026-10-04Python编程

这个采集平台最终用 Docker / systemd 部署在一台 Linux 机器上长跑。长跑的进程我早就不指望它不挂——OOM、发版重启、宿主机维护、甚至掉电都会发生。真正的问题不是"会不会崩"，而是"崩了能不能自己爬起来、一条任务都不丢、也不重复抓一堆"。这篇讲我用 SQLite outbox、崩溃恢复、优雅停机，再加 Redis 去重和 Lua 看门狗把可靠性兜起来的过程。并发模型见asyncio 两级并发那篇，对外抓取的安全校验见SSRF 防护那篇。

一条任务的一生：先看时序图

把 outbox、心跳、看门狗放在一张时序图里，后面的代码就顺了：

 worker :  claim -> SET hb ex=10s -> 干活(每3s续租) -> 成功: DEL hb + 置 done
 sweep  :  每 5s 扫 processing:
            hb 还在 ?  -> alive, 跳过
            hb 没了 ?  -> INCR fail
                          fail < 阈值 -> requeue (UPDATE ... WHERE status='processing')
                          fail >= 阈值 -> dead (死信)
 requeue:  以 SQLite 状态为准，幂等更新，避免 Redis 与库状态不一致

为什么要 outbox：先落库，再干活

最开始任务只活在内存队列里，进程一死就全蒸发。改造思路很朴素：凡是要做的事，先写进本地 SQLite，再去做。任务从 outbox 领走、处理完再更新状态，这样处理到一半崩了，记录还在磁盘上：

CREATE TABLE IF NOT EXISTS outbox (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    url         TEXT NOT NULL,
    source      TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending',  -- pending/processing/done/dead
    fail_count  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

asyncio 里用 SQLite：aiosqlite + WAL

SQLite 是同步阻塞的，直接在事件循环里 execute 会卡住所有协程。我用 aiosqlite 把 IO 丢到线程池，同时开 WAL 模式——读写不再互锁，writer 和 reader 可以并发，多 worker 抢写时也不至于立刻 database is locked：

import aiosqlite

async def init_db(path: str):
    db = await aiosqlite.connect(path)
    await db.execute("PRAGMA journal_mode=WAL")   # 读写不互锁
    await db.execute("PRAGMA busy_timeout=5000")  # 拿不到锁先等 5s 再报错
    return db

崩溃恢复：启动时把 processing 残骸捞回来

正常退出时任务走到 done，崩溃时那些 processing 其实没人收尾。启动第一件事就是把它们重置回 pending：

async def recover_stale(db) -> int:
    cur = await db.execute(
        "UPDATE outbox SET status='pending', updated_at=datetime('now') "
        "WHERE status='processing'")
    await db.commit()
    return cur.rowcount   # 启动日志打一行，直观看到恢复了多少条

优雅停机：收到 SIGTERM 后的四步

Docker / systemd 停服务发的都是 SIGTERM。部署在 Linux 上，我用 asyncio 信号处理分四步：置停止位 → 停止取新任务 → await queue.join() 等在途收尾 → flush 落库再退出。这样停机窗口里的任务要么做完，要么停在 pending 等下次恢复，绝不会停在半中间的 processing。

去重：URL 规范化 + 内容指纹

6 个源交叉转载很多，光给原始 URL 做哈希不够——同一篇文章带不同 utm_* 参数、不同片段，URL 哈希就不一样，还是会重复抓。我先规范化 URL（去追踪参数、去片段、去尾部斜杠），再叠一层正文哈希：

from urllib.parse import urlparse, parse_qsl, urlencode, urlunparse
TRACK = {"utm_source", "utm_medium", "utm_campaign", "utm_term"}

def normalize_url(raw: str) -> str:
    u = urlparse(raw)
    q = [(k, v) for k, v in parse_qsl(u.query) if k not in TRACK]
    return urlunparse(u._replace(fragment="", query=urlencode(q))).rstrip("/")

def seen_before(r, raw: str, body: str) -> bool:
    url_fp = hashlib.sha1(normalize_url(raw).encode()).hexdigest()
    body_fp = hashlib.sha1(body.encode()).hexdigest()[:16]   # 大文本可换 simhash
    key = f"seen:{url_fp}:{body_fp}"
    return r.set(key, 1, nx=True, ex=7 * 24 * 3600) is None

看门狗：心跳续租 + 重放幂等

优雅停机管不住"worker 卡死"。我的做法：worker 领任务时在 Redis 写带 TTL 的心跳 key，处理过程中周期续租，成功就主动删 key（即 ack）：

async def heartbeat_loop(job_id: str, r, working: dict) -> None:
    key = f"hb:{job_id}"
    while working.get(job_id):
        await r.set(key, "1", px=10000)   # TTL 10s，每 3s 续租一次
        await asyncio.sleep(3)
    await r.delete(key)                   # ack：删掉心跳，看门狗就不会误判

清扫协程发现任务还在 processing、心跳却没了，就认定 worker 死了。判断 + 计数 + 决定重放还是熔断必须原子，否则两个清扫协程会同时重放同一条。重放时我顺手删掉失败计数 key，给新 worker 一段宽限，避免"新心跳还没建立"前被二次计数：

watchdog = r.register_script("""
-- KEYS[1]=心跳 key  KEYS[2]=失败计数 key   ARGV[1]=失败阈值
if redis.call("pttl", KEYS[1]) < 0 then
    local n = tonumber(redis.call("get", KEYS[2]) or "0") + 1
    redis.call("set", KEYS[2], n, "EX", 86400)
    if n >= tonumber(ARGV[1]) then
        redis.call("del", KEYS[1])
        return "dead"                    -- 连续失败太多，熔断进死信
    end
    redis.call("del", KEYS[1])            -- 宽限：清心跳，等新 worker 重新续租
    return "requeue"
end
return "alive"
""")

这里还有个跨存储的坑：Redis 说"该重放"，但 SQLite 里这条任务可能已经被别人处理成 done 了。所以重放以 SQLite outbox 状态为准，做幂等更新——只有还停在 processing 才改回 pending：

async def requeue_if_stale(db, job_id: str) -> bool:
    cur = await db.execute(
        "UPDATE outbox SET status='pending', updated_at=datetime('now') "
        "WHERE id=? AND status='processing'", (job_id,))
    await db.commit()
    return cur.rowcount == 1   # 已是 done 则 rowcount=0，直接跳过，不重复发

备选方案与权衡

我的选择备选取舍
SQLite outbox 本地落库纯消息队列（Redis Stream / RabbitMQ）单实例、要简单持久化与崩溃恢复，SQLite 零依赖；多实例消费才需要 MQ 的分区与确认机制
Redis SET NX 精确去重布隆过滤器SET 无假阳性、可按 TTL 淘汰，但内存随去重条数线性涨；布隆省内存但有误判（会误杀少量新文章），且不能删除
心跳 + Lua 看门狗重放只靠 worker 超时异常异常能覆盖"报错退出"，覆盖不了"协程静默卡死"；看门狗是兜后者的最后保险

核心经验：可靠性的本质是"任何时刻进程突然死掉，系统都能从磁盘上的状态自愈"。outbox 先落库不丢任务，WAL 让 SQLite 在 asyncio 下不卡不锁，优雅停机不腰斩在途任务，看门狗 + 幂等重放让卡死任务不被遗忘、也不被重复发。跨存储状态以 outbox 为准——Redis 会误报，SQLite 的条件更新不会。
