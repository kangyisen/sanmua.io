四账户积分记账：余额、冻结、乐观锁与消费优先级

2026-09-25Go设计

做内容产品，积分体系绕不开。我们的积分不是单一池子，而是拆成多个独立账户，各自有不同的过期规则；每个账户还配了冻结字段，配合乐观锁和周期限额。这篇基于真实模型和代码，把「为什么这么分、怎么扣、怎么冻结、怎么记流水」完整讲清楚。

为什么必须分账户

核心原因是不同积分的生命周期不一样。如果合成一个 points 字段，会员到期时到底该清掉多少、哪些是用户花钱买的永久积分，根本算不清。所以分账户、分流水。实际落地是四个账户（比早期文档多了一个「奖励积分」）：

账户字段过期规则来源
奖励积分reward_points活动规则活动 / 奖励发放
会员积分member_points随会员到期清零订阅 / 单买会员时充值
加油包积分boost_points永不过期单独购买积分加油包
普通积分points永不过期签到、盲盒、管理员赠送

UserPoints 表结构

每个用户在每个产品（appId）下有一条积分记录，(user_id, app_id) 联合唯一。除了四个余额，还有四类冻结字段、乐观锁版本号和周期限额三件套：

type UserPointsData struct {
    Points, MemberPoints, BoostPoints, RewardPoints int64 // 四个余额
    FrozenPoints, FrozenMemberPoints,
    FrozenBoostPoints, FrozenRewardPoints int64             // 四个冻结额
    Version    int64              // 乐观锁版本
    PointsLimit int64             // 周期积分上限（0=不限）
    PeriodType PointsPeriodType   // 周期：日 / 周 / 月 / 年 / 不限
    PeriodUsedPoints int64        // 本周期已用
    FrozenPeriodPoints int64      // 本周期已冻结
}

「可用余额」永远是余额减去冻结，冻结中的积分不能被再次消费：

func availablePointBalance(balance, frozen int64) int64 {
    available := balance - frozen
    if available < 0 { return 0 }
    return available
}

消费扣减优先级

聊天扣积分时先扣哪个账户？顺序是 奖励 → 会员 → 加油包 → 普通。逻辑是从用户价值倒推：快过期、活动限定、贵的先用掉，永久有效的留到最后，否则会员积分到期作废会引发投诉。畅聊卡是更上层的全局权益，生效时直接跳过、不扣积分。

分摊算法很简洁，按优先级逐个账户「能扣多少扣多少」，把剩余量往后传：

func allocatePointAccounts(amount, reward, member, boost, normal int64) (int64,int64,int64,int64) {
    remaining := amount
    rewardAmount, remaining := allocatePointAccount(remaining, reward)
    memberAmount, remaining := allocatePointAccount(remaining, member)
    boostAmount,  remaining := allocatePointAccount(remaining, boost)
    normalAmount, _ := allocatePointAccount(remaining, normal)
    return rewardAmount, memberAmount, boostAmount, normalAmount
}
func allocatePointAccount(remaining, available int64) (int64, int64) {
    if remaining <= 0 || available <= 0 { return 0, remaining }
    if available >= remaining { return remaining, 0 }
    return available, remaining - available
}

扣减：一条带满条件的 UPDATE + 乐观锁重试

并发扣减最容易扣成负数。我们在同一条 UPDATE 里同时校验版本、各账户冻结后余额和周期限额，任何一条不满足都不会写：

result := tx.Model(&UserPoints{}).
    Where("id = ? AND version = ?", pointInfo.ID, pointInfo.Version).
    Where("reward_points - frozen_reward_points >= ?", rewardDeduct).
    Where("member_points - frozen_member_points >= ?", memberDeduct).
    Where("boost_points - frozen_boost_points >= ?", boostDeduct).
    Where("points - frozen_points >= ?", normalDeduct).
    Where("points_limit <= 0 OR period_type = ? OR
           points_limit - period_used_points - frozen_period_points >= ?", NoLimit, amount).
    Updates(updateFields) // 内含 version = version + 1
if result.RowsAffected == 0 { return errPointsConcurrentConflict }

影响行数为 0 说明这期间版本被别的事务改过（或余额 / 限额不足），外层捕获冲突后重试，最多 3 次，仍失败返回「系统繁忙」。这就是「分布式锁串行 + 乐观锁兜底」的配合。

扣减前还有两道前置判断：总可用不足 → ErrorPointsInsufficient；开启了周期上限且本周期额度耗尽 → ErrorPointsPeriodExhausted。

流水：跨账户一次扣减产生多条

每笔变动都写 PointsRecord，带 BeforePoints / AfterPoints、账户类型、交易方向（收入 / 支出）、关联订单。一次消费若横跨两个账户，就产生两条流水，保证每个账户都能独立对账：

record := PointsRecord{
    AccountType: accountType, Points: points,
    BeforePoints: beforePoints, AfterPoints: beforePoints - points,
    TradeType: TradeTypeOut, RecordType: recordType,
}

入账：和扣减用同一把锁

积分入账散落在签到、履约、后台赠送等很多地方，统一收口到 PointsIncome。一个关键点：入账也加 points_consume:{appId}:{userId} 锁，和扣减是同一把，保证入账与扣减互斥，不会读到中间态：

func PointsIncome(appId, userId SfID, points int, remark string,
    recordType RecordType, accountType AccountType, orderId SfID, tx *gorm.DB) error {
    locked, _ := cache.LockAndWait(getPointsLockKey(appId, userId), 30*time.Second)
    defer cache.Unlock(lockKey)
    return pointsIncomeInTx(appId, userId, points, remark, recordType, accountType, orderId, tx)
}

核心逻辑按账户类型选字段，先写流水、再用 gorm.Expr("字段 + ?") 原子加。同时提供 PointsIncomeInTx 无锁版——当调用方已经持有这把锁（比如履约引擎在订单处理事务内），避免重复加锁、也避免锁重入死锁。

冻结机制：先占额度，成功再扣、失败就放

有些场景要「先占住积分、业务成功才真扣」（比如生成内容前先冻结，生成失败要退还）。这就是两阶段冻结，状态为 Frozen → Consumed / Released，默认 30 分钟 TTL：

FreezePointsWithRequestID(...) // 冻结：增加 frozen_*，占用可用额度
ConsumeFrozenPoints(...)        // 确认：冻结转真实扣减
ReleaseFrozenPoints(...)        // 释放：退回 frozen_*，恢复额度

冻结请求支持传 requestID 做幂等：同一 requestID 重复请求，已冻结则报频繁、已消费则直接返回原记录，防止网络重试导致重复冻结。还提供 ConsumeFrozenPointsWithTransaction，把「业务执行 + 确认扣冻结」放进同一个数据库事务，业务失败则整体回滚、冻结不会被误扣。

AfterFind：读取时自动维护过期与周期

模型的 AfterFind 钩子在每次读取时做轻量维护，省掉了一批定时任务：

  • 各余额 / 冻结若为负，归零兜底；
  • 会员积分有余额且已过 member_points_expired_at，直接清零；
  • 周期重置：按 PeriodType 判断是否跨日 / 跨周（ISOWeek）/ 跨月 / 跨年，跨了就把 period_used_points 清零并落库。

会员到期：清零，不转普通积分

RevokeMembership 在会员到期时把会员积分直接清零，并写一条「会员到期，积分已过期」的支出流水，不再转入普通积分（早期做过转换，产品后来取消）。历史在流水里仍可追溯。

这套设计的核心有两条：不同生命周期的钱必须放进不同账户，一个字段存所有积分，迟早会在过期规则和对账上爆炸；以及「冻结占额 + 乐观锁 + 全条件 UPDATE」共同保证并发下不超扣、不错扣。余额会骗人，带条件的更新和流水不会。
