三账户积分设计：普通积分、会员积分与加油包的记账与消费优先级

2026-09-25Go设计

做内容产品，积分体系是绕不开的。我们的积分不是单一池子，而是拆成了三个独立账户，各自有不同的过期规则和来源。一开始图省事想塞在一个字段里，后来发现会出大问题，记录一下设计过程。

为什么要拆三个账户

业务上有三种积分，过期规则完全不同：

账户DB 字段过期规则主要来源
普通积分points永不过期签到、盲盒奖励、管理员赠送
会员积分member_points随会员到期一起过期订阅 / 单买会员时充值
加油包积分boost_points永不过期单独购买的积分加油包

如果合成一个 points 字段，就没法区分哪些积分随会员过期、哪些永远有效——会员到期时到底要清掉多少？算不清。所以必须分账户、分流水。

消费扣减优先级

用户聊天要扣积分时，先扣哪个账户？业务定的优先级是：

畅聊卡（有效期内直接跳过，不扣积分）
  → 会员积分（最贵、会过期，先用掉）
  → 加油包积分
  → 普通积分（最便宜、永不过期，留到最后）

这个顺序是从「用户价值最大化」倒推的：快过期、贵的先扣，便宜的、永久的后扣。不然会员积分留在账户里过期作废，用户会来投诉。

入账和流水统一收口

积分入账散落在很多地方：签到、履约、管理员调整、会员到期转换。如果每个地方都自己写 UPDATE user SET points = points + ?，迟早漏。所以统一收口到一个函数：

user.PointsIncome(userId, points, remark, recordType, accountType, tx)

它必须在事务内调用，同时写账户余额和流水记录。每一笔积分变动都有流水可查，出了问题能对账。

并发扣减怎么不超扣

用户并发发两条消息，可能同时读同一个积分余额，都判断「够」，都扣，结果扣成负数。两个手段：

  • 分布式锁 points_consume:{userId}，把同一用户的扣减串行化；
  • 数据库兜底：扣减 SQL 写成 UPDATE ... SET points = points - ? WHERE points >= ?，影响行数为 0 就是余额不足。

踩过的坑

  • 会员积分过期不能硬删：会员到期时不能直接把 member_points 清零，要按业务规则处理（我们早期做过「会员到期转普通积分」，后来产品取消了这个逻辑，但流水里要能查到历史）。
  • 金额用整数不用浮点：积分本质是钱，DB 里用 int64，展示层再格式化，避免浮点误差。

这套设计的核心是：不同生命周期的钱，必须放在不同的账户里。一个字段存所有积分，短期省事，长期一定在对账和过期规则上爆炸。
