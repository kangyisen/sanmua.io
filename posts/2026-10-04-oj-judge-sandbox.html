OJ 判题沙箱：FastAPI 微服务与 Docker 隔离评测

2026-10-04PythonDocker编程

主站负责题目、提交、排行榜，本身是典型的 Web 业务。但「跑用户提交的代码」这件事天生和 Web 不是一类工作：它不可信、吃资源、语言五花八门。把它和主站揉在一个进程里，等于把陌生人的代码放进自己的内存空间。所以在这个在线判题系统里，我把评测单独拆成一个 FastAPI 微服务，用 Docker 做隔离。这篇讲清楚为什么要拆、一次提交怎么跑、容器的 CPU/内存/时间/网络到底怎么限。

为什么把判题从主站解耦出去

一开始我也想图省事，在主站里直接起进程跑用户代码。做了两天就放弃了，理由很现实：

  • 安全：用户代码里写 os.system("rm -rf /")、读宿主环境变量、连内网数据库，主站进程会跟着遭殃；
  • 资源隔离：一份死循环或者超大数组不能把整个主站拖垮；
  • 可独立扩缩：评测是 CPU 密集且排队的活儿，主站闲、评测忙时只加评测节点即可；
  • 语言镜像独立：C/C++、Python、Java 用各自的基础镜像，升级一种语言不碰其他。

于是主站只做一件事：接收提交，丢进队列，把结果写库。真正跑代码的全在判题服务里。

一次提交的完整评测流水线

判题服务从队列拿到一条提交后，流程是固定的几步：拉题目与测试点 → 起容器 → 编译 → 逐个测试点运行并比对 → 回收容器。FastAPI 这层很薄，只做路由和编排，重活全交给容器：

@app.post("/judge")
async def judge(submission: SubmissionIn):
    # 1. 从题目服务拉测试点（示例：内存里取，真实走题目微服务）
    problem = await problem_client.fetch(submission.problem_id)
    # 2. 丢进异步任务，立刻返回，评测在后台慢慢跑
    asyncio.create_task(run_case(submission, problem))
    return {"status": "queued", "submission_id": submission.id}

评测不阻塞接口，前端轮询或等回调拿结果，这是判题服务能扛住并发提交的前提。

用 Docker SDK 起一个受限容器

核心是跑起来之前把「权限」先收紧。我用官方 docker Python SDK，一次 containers.run 把 CPU、内存、网络、文件系统都限死：

import docker
client = docker.from_env()

def run_in_container(image, cmd, source_dir, time_limit, mem_limit):
    return client.containers.run(
        image=image,
        command=cmd,
        volumes={source_dir: {"bind": "/workspace", "mode": "rw"}},
        working_dir="/workspace",
        detach=True,
        remove=True,                 # 跑完自动删，不留垃圾容器
        network_disabled=True,        # 断网，杜绝反向连外网/内网
        mem_limit=f"{mem_limit}m",   # 内存硬上限
        nano_cpus=int(0.5 * 1e9),     # 等于 --cpus 0.5，半核
        read_only=True,              # 根文件系统只读
        tmpfs={"/tmp": "size=64m"},  # 只给 /tmp 一块可写临时卷
    )

这里几个参数是「被生产环境教出来的细节」：network_disabled 直接断掉网络，比任何防火墙规则都干净；read_only 加 tmpfs 是因为程序运行时难免要写临时文件，全只读会误杀正常程序，于是只放行一块明确大小的临时盘。

时间限制：超时必须硬杀

CPU 和内存靠 Docker 内核层面限制，但「超时」不能只靠容器自己掐。死循环的进程不会自己退出，必须由外部看门狗在到点时强制结束：

import time

def run_with_timeout(container, time_limit_s):
    start = time.time()
    result = container.wait()   # 阻塞等容器结束
    elapsed = time.time() - start
    if elapsed > time_limit_s or container.status == "running":
        container.kill()        # 到点还在跑，直接杀掉，判 TLE
        return {"verdict": "TLE", "elapsed": elapsed}
    return {"verdict": "OK", "elapsed": elapsed}

判 TLE（Time Limit Exceeded）的依据是「墙钟时间超过阈值就 kill」，而不是等它自己跑完。内存超限则由 Docker 的 mem_limit 触发 OOM，进程被内核杀掉，对应 MLE。

编译与逐测试点比对

不同语言的动作不一样：C/C++ 要先 g++ 编译再运行，Python/Java 视情况直接解释运行。编译失败直接判 Compile Error；编译过了，再把每个测试点的输入喂进容器，拿标准输出和期望输出逐行比对：

def evaluate(proc_out, expected):
    # 忽略末尾空行差异，避免 PE 误判
    out = proc_out.strip().splitlines()
    exp = expected.strip().splitlines()
    if out == exp:
        return "AC"
    return "WA"

编译和运行用不同镜像阶段：编译镜像带编译器，运行镜像尽量精简，两者职责分开，也让运行时更安全。

用 Compose 一键编排判题服务

判题服务本身依赖题目接口、队列、数据库，手起手停很容易漏。我把它写进 docker-compose.yml，评测服务和依赖一起拉起，privileged 之外不额外放权——它自己要能起子容器，所以挂了宿主的 /var/run/docker.sock：

services:
  judge:
    build: ./judge
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    deploy:
      resources:
        limits:
          memory: 2g

挂 docker.sock 意味着判题服务拥有「起容器」的能力，这是它能当沙箱父进程的前提；但每一个被它起的评测容器又都被限得很死，形成「父服务有权限、子任务被关在笼子里」的两层结构。

核心经验：判题的本质不是「跑代码」，而是「在可信的边界内跑不可信的代码」。把评测拆成独立微服务，是为了让安全和资源问题被集中处理一次；Docker 的 CPU、内存、网络、只读根文件系统则是这道边界的具体落地。永远假设用户的代码会搞破坏，然后让任何破坏都被关在一个跑完即删的容器里。
