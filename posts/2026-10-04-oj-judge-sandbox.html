OJ 判题沙箱：FastAPI 微服务与 Docker 隔离评测

2026-10-04PythonDocker编程

主站负责题目、提交、排行榜，是典型 Web 业务。但「跑用户提交的代码」天生和 Web 不是一类工作：它不可信、吃资源、语言五花八门。这个在线判题系统里我把评测单独拆成 FastAPI 微服务，用 Docker 做隔离。这篇讲清楚为什么拆、一次提交怎么跑、容器怎么限资源，以及一个被我自己写错又修回来的 TLE 判定 bug。配套的出题侧见LLM Agent 自动出题。

一次提交的端到端流水

主站只做接收与写库，评测在后台队列里跑。整条链可以画成这样：

用户提交
   |
   v
主站 API --写入--> 评测队列(Redis)
                        |
                        v
                 判题 worker (FastAPI 后台任务)
                        |
                        +-- 拉取题目/测试点
                        +-- 起 Docker 容器(限资源)
                        +-- 编译 -> 喂输入 -> 收集输出 -> 比对
                        +-- 回收容器
                        |
                        v
                 结果回写主站(AC/WA/TLE/MLE/CE)

FastAPI 这层很薄，路由只负责把提交丢进异步任务就返回，真正跑代码的全在容器里：

@app.post("/judge")
async def judge(submission: SubmissionIn):
    asyncio.create_task(run_submission(submission))  # 后台慢慢跑
    return {"status": "queued", "submission_id": submission.id}

起容器：一道参数就是一道防线

用官方 docker Python SDK，跑之前先把权限收紧。下面这版补全了之前漏掉的几项硬限制，每项都对应一类真实攻击：

import docker
client = docker.from_env()

def start_runner(source_dir, time_limit, mem_limit=256, cpu_limit=0.5):
    return client.containers.run(
        image="oj-runner:py311",
        command=["python", "main.py"],
        volumes={source_dir: {"bind": "/workspace", "mode": "rw"}},
        working_dir="/workspace",
        detach=True,
        # 资源：内存硬上限 + 半核（示例默认值）
        mem_limit=f"{mem_limit}m",
        nano_cpus=int(cpu_limit * 1e9),   # 等价 --cpus 0.5
        pids_limit=64,                   # 防 fork 炸弹：进程数封顶
        # 权限：丢弃 capabilities、禁止提权
        cap_drop=["ALL"],
        security_opt=["no-new-privileges"],
        # 文件系统：根只读，只给 /tmp 一块临时可写盘
        read_only=True,
        tmpfs={"/tmp": "size=64m"},
        # 网络：彻底断网
        network_disabled=True,
    )

逐项说意图：pids_limit 挡 fork 炸弹（while True: os.fork()）；cap_drop=["ALL"] 丢掉容器默认拿到的 Linux capabilities，no-new-privileges 禁止 setuid 提权；read_only 加 tmpfs 是因为程序难免写临时文件，全只读会误杀正常程序，于是只放行一块明确大小的临时盘；network_disabled 断网，比防火墙规则干净。

TLE 判定：我写错过的那版

这是这篇最想讲清楚的坑。我第一版是这么写的——看起来对，其实超时永远触发不了：

# 错误示范：wait() 会一直阻塞到进程自己结束
start = time.time()
container.wait()                 # 死循环在这里永远等不回来！
elapsed = time.time() - start    # 这行根本执行不到
if elapsed > time_limit_s:
    container.kill()

问题在于死循环进程不会自己退出，wait() 阻塞到天荒地老，后面的超时判断成了死代码。正确做法是让看门狗和 wait 并发：一条线程负责「到点强杀」，主线程负责「等它正常结束」，谁先到算谁：

import threading, time

def run_with_watchdog(container, time_limit_s):
    killed_by_watchdog = {"on": False}

    def watchdog():
        time.sleep(time_limit_s)          # 到点了还没退出
        if container.status == "running":
            killed_by_watchdog["on"] = True
            container.kill()              # SIGKILL，强制结束

    t = threading.Thread(target=watchdog, daemon=True)
    t.start()
    ret = container.wait()                 # 正常结束会先返回
    exit_code = ret["StatusCode"]
    container.reload()
    if killed_by_watchdog["on"]:
        return {"verdict": "TLE"}          # 墙钟超时被强杀
    if exit_code == 137:                   # 128+9 SIGKILL，多为 OOM
        return {"verdict": "MLE"}
    return {"verdict": "RUN_OK", "exit_code": exit_code}

判据要点：TLE = 墙钟时间到点被看门狗 SIGKILL。这里必须区分两个时间——墙钟时间（真实流逝秒数）和 CPU 时间（进程实际占用 CPU 的秒数）。在 nano_cpus 限流下，一个进程跑满半核时墙钟 1 秒只换到约 0.5 秒 CPU，二者不再相等。OJ 传统上用墙钟做 TLE 上限（用户可感知），如果要更精细，可再取容器的 CPU 用量：

stats = container.stats(stream=False)
cpu_delta = stats["cpu_stats"]["cpu_usage"]["total_usage"] - \
            stats["precpu_stats"]["cpu_usage"]["total_usage"]

编译→喂输入→收输出→比对的完整链路

光起容器不够，还得把测试点输入喂进去、把输出捞出来。我走「挂载文件」的方式：把测试点输入写成 input.txt 挂进容器，程序从标准输入读，跑完再从容器日志里取 stdout：

def evaluate_one(problem, workdir):
    # 1. 编译（C/C++ 为例，解释型语言跳过这步）
    compile_in_container(workdir, src="main.cpp")
    results = []
    for i, case in enumerate(problem.test_cases):
        write_input(workdir, case["input"])      # 落盘 input.txt
        c = start_runner(workdir, time_limit=problem.time_limit)
        verdict = run_with_watchdog(c, problem.time_limit)
        # 2. 先取日志、再决定回收，顺序很关键（见下节）
        out = c.logs(stdout=True, stderr=False).decode().strip()
        err = c.logs(stdout=False, stderr=True).decode().strip()
        c.remove()                               # 手动回收
        results.append(judge(case["output"], out, verdict, err))
    return results

比对时忽略末尾空行差异，避免 Presentation Error 误判；编译失败单独判 CE，不进入运行环节。

remove=True 的时序陷阱

上面我特意用 detach=True 起、最后手动 c.remove()，而不是 remove=True。原因是时序：remove=True 会在容器一停止就立刻删掉它——一旦进程被看门狗 kill 掉，容器马上销毁，你再去 container.logs() 就会报「No such container」，CE 的报错信息和 WA 的真实输出全都拿不到。所以正确顺序是先 wait / logs 取完，再 remove。

挂 docker.sock 的风险，以及加固方案

判题服务要能「起子容器」，就得挂宿主的 /var/run/docker.sock。这一步等于把宿主 root 权限交给了这个服务——一旦判题服务自身被攻破，攻击者就能直接在宿主上起特权容器。我没有回避它，而是把可选加固方案列清楚，按取舍选：

方案隔离强度代价 / 取舍
原生 Docker + 挂 sock中最简单，但挂 sock ≈ 宿主 root
gVisor (runsc)高用户态拦截 syscall，冷启动略慢
rootless Docker中高非 root 跑 daemon，攻击面小，部分特性受限
独立评测机 + 受限 API最高评测节点与主网络隔离，需额外运维

gVisor 是我觉得性价比最高的折中：给 runner 镜像换 runtime=runsc 即可，syscall 被拦在用户态，即使容器被突破也很难触到宿主内核。规模再大就上独立评测机，把它放在单独网段，主站只能通过一个受限的提交接口投递任务。

备选方案与权衡

  • Docker vs gVisor vs 虚拟机：Docker 冷启动最快、隔离最弱；gVisor 在中间；每个测试点开一台完整虚拟机隔离最强但冷启动秒级、吞吐低。OJ 高频短任务，我选 Docker/gVisor，不选 VM；
  • 队列上限与扩缩：worker 设并发上限（示例 4），队列堆积时只加评测节点，不碰主站——这正是当初要解耦的原因。

核心经验：判题的本质不是「跑代码」，而是「在可信边界内跑不可信代码」。TLE 不是靠「等它超时」而是靠看门狗与 wait 并发强杀；隔离不是一个 run 参数，而是 mem/cpu/pids/cap_drop/read_only/network 一整套。永远假设用户代码会搞破坏，然后让任何破坏都被关在一个跑完即删的容器里。
