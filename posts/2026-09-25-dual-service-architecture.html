一个仓库拆出 C 端 App 与 B 端后台：双服务架构实践

2026-09-25Go架构

最近在做一个 AI 角色扮演 / 剧本社交平台，后端基于 gin-vue-admin（GVA）二开。它同时要服务两类用户：手机端的 C 端用户，和公司内部的 B 端管理后台。这两类服务的诉求几乎是反的，最后落在了「一个仓库、一个镜像、两个入口」的方案上。这篇把目录、路由、鉴权、响应封装的真实实现完整记录下来。

为什么要拆

  • C 端面向海量移动端用户：接口要轻、鉴权要快、要统计 DAU、错误要按 Accept-Language 多语言；
  • B 端是内部管理：要 Casbin RBAC、操作日志、复杂管理列表，用户量小但权限细。

塞在一个路由组里，中间件会变成「如果是管理接口怎样、App 接口又怎样」的层层 if。拆成两个进程，端口、鉴权、日志、Swagger 文档都各管各的。

两个入口：90% 相同，顺序有讲究

C 端入口 cmd/app/main.go（端口 9259），B 端入口 cmd/platform/main.go（端口 9258）。主体流程几乎一样，但有几处真实差异：

// cmd/app/main.go
global.GVA_VP = internal.Viper()
initialize.OtherInit()
global.GVA_LOG = internal.Zap()
zap.ReplaceGlobals(global.GVA_LOG)
errors.LoadI18n(); event.LoadI18n()
global.GVA_DB = db.Gorm()
db.RegisterTables()        // AutoMigrate
cache.Init()
app.AppInit()              // C 端业务初始化（注册 cron 等）
initialize.Timer()
internal.RunServer(router.Routers())

// cmd/platform/main.go —— 多了 db.DBList() 和 platform.Init()
global.GVA_DB = db.Gorm()
db.DBList()                // 多数据源（B 端独有）
db.RegisterTables()
app.MgmInit()              // 管理端业务初始化
cache.Init()
initialize.Timer()
platform.Init()            // B 端框架初始化（字典/数据源等）
internal.RunServer(router.Routers())

两边都支持环境变量 SKIP_AUTO_MIGRATE=1 跳过启动迁移，本地能省十几秒。共享的启动引导（Viper 读配置、Zap 建日志、Gin 引擎、最终 ListenAndServe）都收在 cmd/internal/，两个入口只负责「按什么顺序装配」。

目录：共享的下沉，专属的分开

server/
├── cmd/
│   ├── app/          # C 端 main.go + 专属路由
│   ├── platform/     # B 端 main.go + 专属路由（GVA 框架）

├── api/v1/
│   ├── app/          # C 端 handler
│   ├── platform/     # B 端 handler
│   └── internal/     # handler 包装器（鉴权模式）
├── services/
│   ├── app/          # C 端业务逻辑（30+ 业务包）
│   ├── platform/     # B 端框架功能
│   └── common/       # 共享：错误码、HTTP 封装、存储、第三方 SDK

路由演进：从单一路径到「多产品」分治

这是文档里没怎么提、但实际很关键的一块。随着业务扩张，C 端路由已经不只是 /v1/app/*，而是按产品 / 端拆成了多组：

func Routers() *gin.Engine {
    engine := internal.InitWebEngine()
    app.InitAppSwagger(engine)

    app.InitInternalRouter(engine.Group("/v1/internal"))

    // 核心业务：/v1/:product，第一个产品 code=app，老客户端零感知
    group := engine.Group("/v1/:product")
    app.InitBusinessAppRouter(group)

    genesis.InitRouterV2(engine.Group("/v1/genesis"))   // 独立产品 V2 契约
    og := engine.Group("/v1/odyssey")                   // 第三版移动 API
    og.Use(app.OdysseyProductContext())
    app.InitOdysseyRouter(og)
    app.InitCreatorRouter(engine.Group("/v1/creator"))   // 创作者平台
    web.InitBusinessWebRouter(engine.Group("/v1/web"))
    officialwebsite.InitBusinessOfficialWebsiteRouter(
        engine.Group("/v1/officialWebsite"))
    return engine
}

用 :product 路径参数而不是写死 app，是为了让同一套 handler 服务多个产品，产品上下文在包装器里校验并注入。

Handler 包装器：业务只返回 (data, error)

C 端没有用标准 Gin handler（直接写 c.JSON），而是定义了函数式签名，由包装器统一处理鉴权、panic、响应：

type HandlerFunc func(ctx *http.Context) (interface{}, error)

// 5 种鉴权模式
AppAuth(h)     // 必须登录，记录 DAU，失败 401
SelectAuth(h)  // 登录了就拿用户信息，没登录也放行
NoAuth(h)      // 完全开放
CreatorAuth(h) // 创作者 token，与 C 端 b_user 物理隔离
InternalAuth(h)// 内部服务 token（X-Internal-Token，恒定时间比较）

包装器 Wrapper 内部做了三件值得说的事：

1. 产品上下文注入。从 :product 取 code，查 product.GetByCode，查不到直接 404，避免脏数据写进错误产品；非产品路由（creator/web 等）没有该参数则跳过：

code := c.Param("product")
if code == "" {
    if fixed, ok := c.Get("fixedProductCode"); ok { code, _ = fixed.(string) }
}
if code != "" {
    p, pErr := product.GetByCode(code)
    if pErr != nil { ctx.NotFound(); return }
    ctx.SetAppId(p.ID)
}

2. panic recovery + 堆栈。defer 里 recover，把 panic 转成内部错误，并打印完整调用栈；同时检查 ctx.Writer.Written()，给 WebSocket 升级放行（连接已被接管，不能再写 HTTP 响应）。

3. 日志里 token 脱敏。记录请求时 x-token 会被替换成 <redacted>，防止 token 落进日志文件。

自定义 Context 与统一响应

http.Context 内嵌 *gin.Context，额外挂了 DB、LOG、用户信息、Language、appId，以及类型化参数方法（SfID() / IntParam()）。HTTP 状态码遵循「首错优先」：4xx 之间不互相覆盖，5xx 可以覆盖 4xx。

响应统一为 {"code":0,"msg":"success","data":{}}，出错时 ResponseWrapper 按错误类型映射：

switch exp := err.(type) {
case validator.ValidationErrors: // 参数校验错误 → i18n
    response["code"] = errors2.CommonInvalidParams
case *errors2.Error, errors2.Error: // 自定义错误 → 错误码 + i18n
    response["code"] = exp.ErrorCode
default: // 兜底未知错误
    response["code"] = errors2.CommonUnknownError
}
if ctx.GetBool(NumericCodeContextKey) { // genesis 产品要求数字码
    response["code"] = numericErrorCode(ctx, err)
}

字符串错误码（如 auth.token.invalid）是主格式；genesis 这类新契约要求标准 HTTP 数字码，通过 context key 切换，两套并存。

JWT：用户信息全在 token 里，缓存只管下线

鉴权用 HS256，token 从 x-token header 读（WebSocket 回退到 ?x-token=）。一个关键设计是：用户基本信息（UserId/Level/Email）全部编码进 JWT，Redis / 本地缓存只用来控制超时和强制下线，不存用户信息：

// 生成 token 后，缓存一个标记位 b_token_{userId}
cache.Set(fmt.Sprintf("b_token_%d", user.UserId), multiLoginFlag, ttl)

// 校验：先验 JWT 签名，再（开启 TokenLimit 时）查缓存
if config.Business.AppConfig.TokenLimit {
    if err := checkCache(ctx, ctx.user.Expired); err != nil {
        return errors2.ErrorAuthTokenInvalid
    }
}

多点登录（MultiLogin=false）时，缓存值记录登录 IP，换设备登录会刷新标记，旧 token 再请求即失效，实现「踢人」。还有个容错：开启多点登录时若缓存读不到（Redis 抖动 / key 丢失），会用合法 JWT 把缓存自愈重建，而不是误杀在线用户。

B 端复用 C 端业务，少写一半代码

B 端经常要管理 C 端数据（审核用户、看订单、发公告）。我们没有在 services/platform/ 再写一套，而是 Platform handler 直接 import services/app/ 复用，外层只加 Casbin 鉴权和操作日志中间件。B 端不存在独立业务 Service 层，避免两套逻辑漂移。框架功能（用户/菜单/字典等）仍走 GVA 的 enter.go struct embedding 管理。

部署：单镜像双命令

同一个 Go 镜像 go-admin-server，docker-compose 起两个容器，启动命令分别是 ./app -c config-app.yaml 和 ./platform -c config-platform.yaml，network_mode: host，健康检查分别探 9259 / 9258，Nginx 按路径反代（/api/ → C 端，/platform/ → B 端）。镜像只构建一次。

这套拆法的核心不是「微服务」，而是「同一套代码，按入口分治」：两个进程共享 80% 的模型与公共逻辑，只在入口、鉴权、响应风格上分道扬镳。对中小团队，比真拆两个仓库靠谱得多。
