asyncio 两级并发：高吞吐采集器的并发模型与热同步

2026-10-04Python编程

写这个多站点市场资讯采集平台时，最开始我把 6 个数据源的任务一股脑塞进同一个 asyncio.Queue，开几十个 worker 一起跑。结果很快被现实教做人：某一个站点限流很严，被打爆后一直返回 429，别的正常站点也跟着排队受连累；想把某个源的并发度从 8 调到 4，还得把整个进程重启。最后我把并发拆成了两层——数据源级和单源内任务级，再加一套不重启的配置热同步。这篇基于真实代码，讲清楚这个模型是怎么搭起来的。

为什么要拆成"两级"并发

采集器面对的不是一个接口，而是 6 个数据源、5 种页面形态。它们的限速能力、超时、稳定性完全不同。如果只有一层"全局 N 个协程"，就没法对单个源做精细限流，一个慢源会拖住整体吞吐。拆成两级后，职责很清楚：

  • 第一级，数据源级：控制同时有多少个数据源在跑，以及每个源对外发起的请求总量，避免某个源被我们自己打挂；
  • 第二级，单源内任务级：在一个源内部，把待抓 URL 放进队列，用固定数量的 worker 并发消费。

第一级：数据源级信号池，互相不连累

我给每个源配一把独立的信号量 asyncio.Semaphore，它就是这个源对外的"在途请求预算"。无论单源内开多少 worker，真正发请求前都要先拿到这把信号，超出预算的自然排队：

async def crawl_one(name: str, cfg: dict, job: dict) -> None:
    # 单源内再压一层：在途请求数被锁死在 cfg["concurrency"] 以内
    async with limiters[name]:
        async with sess.get(job["url"], timeout=CLIENT_TIMEOUT) as resp:
            if resp.status == 429:
                await asyncio.sleep(cfg["backoff"])   # 被限流，退避后这条任务还在队列里
                return
            await parse_and_save(name, resp)

这样一来，A 源再慢、再被限流，也只会占满自己那把信号量，B 源的信号量根本不受影响。限流是按源隔离的，不是全局一刀切。

第二级：单源内 Queue 分发 + worker

每个源内部是一个标准的"生产者—消费者"：生产者把待抓 URL 填进 asyncio.Queue，几个 worker 从队列里取任务干活。队列我设了上限，配合后面的背压：

async def fetch_worker(name: str, cfg: dict, queue: asyncio.Queue) -> None:
    while True:
        job = await queue.get()
        try:
            if job is None:        # 毒丸：收到就退出，用于缩容和停机
                return
            await crawl_one(name, cfg, job)
        finally:
            queue.task_done()      # 无论成功失败都要标记，否则 join 永远不返回

这里有个血泪细节：task_done() 必须放在 finally 里。任务一旦抛异常却没 task_done，queue.join() 就会永远等下去，整个源卡死。

编排：create_task 管 worker，gather 收尾

启动一个源时，我用 create_task 把 worker 都跑起来，生产者灌完队列后 await queue.join() 等所有任务消化完，再发毒丸、用 gather 收尾：

async def run_source(name: str, cfg: dict, queue: asyncio.Queue) -> None:
    workers = [
        asyncio.create_task(fetch_worker(name, cfg, queue))
        for _ in range(cfg["concurrency"])
    ]
    await fill_queue(name, cfg, queue)     # 生产者：把待抓 URL 塞进去
    await queue.join()
    for _ in range(cfg["concurrency"]):
        await queue.put(None)              # 毒丸：通知每个 worker 退出
    await asyncio.gather(*workers)

为什么用 create_task 而不是直接 gather(crawl_one(...)) 一把梭？因为任务是源源不断从队列里来的，worker 要长期存活、循环消费，不是"列出一批任务然后等完"那种一次性场景。

背压：队列有界，别让内存先崩

采集最容易忽略的不是 CPU，是内存。如果队列无界，生产速度远大于消费速度时，待抓任务会在内存里无限堆积。我给每个源的 Queue 设了 maxsize：队列满了，生产者 await queue.put(job) 会自然阻塞，反过来压制抓取节奏。背压不是外加的，是靠有界队列白送的。

层级控制对象用什么做
数据源级单个源对外的在途请求数asyncio.Semaphore
单源内任务级worker 数量与队列缓冲asyncio.Queue(maxsize) + create_task
全局背压内存里堆积的待抓任务有界队列反压生产者

配置热同步：并发度不重启就改

线上最烦的就是改个并发度还要重启进程——重启会丢掉在途任务、还得重新走一遍崩溃恢复。我的做法是起一个独立的协程，定时看配置文件的修改时间，变了就重新加载，把新配置放进一个共享字典：

async def config_reloader(state: dict, path: str) -> None:
    mtime = 0.0
    while True:
        await asyncio.sleep(5)
        try:
            new_mtime = os.path.getmtime(path)
        except OSError:
            continue
        if new_mtime == mtime:
            continue
        mtime = new_mtime
        with open(path, encoding="utf-8") as f:
            state["cfg"] = json.load(f)   # 整体替换，下一轮调度读新值

worker 不直接读死配置，而是每轮从 state["cfg"] 拿当前值。这样改完配置文件，最多 5 秒生效，进程纹丝不动。

被生产环境教出来的细节：信号量大小没法在线改

这里有个坑：asyncio.Semaphore(n) 的 n 一旦创建就改不了，你不能指望"热同步"直接把信号量从 8 调成 4。所以缩容我靠的是 worker 数量——维护一个 worker 集合，目标并发度变小就多发毒丸让多余 worker 自然退出，变大就 create_task 补人：

async def managed_pool(name: str, state: dict, queue: asyncio.Queue) -> None:
    workers = set()
    while True:
        target = state["cfg"][name]["concurrency"]
        while len(workers) < target:           # 扩容
            t = asyncio.create_task(fetch_worker(name, state["cfg"], queue))
            workers.add(t)
            t.add_done_callback(workers.discard)
        while len(workers) > target:           # 缩容：发毒丸让 worker 跑完自己退
            await queue.put(None)
            await asyncio.sleep(0)
        await asyncio.sleep(2)

核心经验：并发不是"开越多协程越快"，而是"按数据源隔离预算、用有界队列做背压、让配置在线可调"。两级并发的本质，是把"对单个目标的礼貌"和"对整体吞吐的追求"解耦——慢源不拖死快源，改配置不打扰在途任务。
