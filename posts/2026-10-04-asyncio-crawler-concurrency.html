asyncio 两级并发：高吞吐采集器的并发模型与热同步

2026-10-04Python编程

写这个多站点市场资讯采集平台时，最开始我把 6 个数据源的任务一股脑塞进同一个 asyncio.Queue，开几十个 worker 一起跑。结果很快被现实教做人：某一个站点限流很严、一直返回 429，别的正常站点也跟着排队受连累；想把某个源的并发度从 8 调到 4，还得把整个进程重启。最后我把并发拆成了全局 + 数据源 + 单源内三层，再加一套不重启的配置热同步。这篇基于真实代码讲清这个模型，其中可靠性兜底见采集可靠性那篇，对外抓取的安全校验见SSRF 防护那篇。

整体长这样：一张 ASCII 架构图

先把三层关系画出来，后面的代码都对着这张图看：

          global_sem  (同时活跃源 <= GLOBAL_ACTIVE_SOURCES)
         ┌───────────────┴────────────────┐
      source1                           source2
     sem_s1 (在途 <= concurrency)      sem_s2 ...
     /  |  \                             /  |  \

    │    │    │                         │    │

    └─ worker 只负责"取任务、跑 crawl_one"
    └─ sem_s1 在 crawl_one 内部真正发请求时才占位

为什么"每源信号量 + 固定 worker"不冗余

刚拆的时候我也怀疑：既然单源内已经固定开了 N 个 worker，再配一把 Semaphore(N) 不就是重复限制吗？不是，它俩管的不是一回事：

  • worker 数量控制"并发消费队列的协程数"和背压节奏——worker 少，队列消费慢，生产者自然被反压；
  • 信号量兜住单条任务内部的二次 fan-out：抓一个详情页往往要再请求图片、接口、分页，一个任务会扇出好几个子请求；信号量保证无论内部怎么扇，这个源对外的在途请求总数始终被压在预算内。

所以 worker 决定"同时几条任务在跑"，信号量决定"这些任务加起来最多打出去多少个请求"。两者是正交的。

全局信号量：同时活跃的源也得限流

第一级往上再套一层：6 个源如果一启动就全部开抓，瞬间把连接和内存都顶满。我加一把全局信号量控制"同时有几个源在跑"，拿不到的源先排队：

GLOBAL_ACTIVE_SOURCES = 2   # 示例：同一时刻最多抓 2 个源
global_sem = asyncio.Semaphore(GLOBAL_ACTIVE_SOURCES)

async def supervise(name: str, cfg: dict, queue: asyncio.Queue) -> None:
    async with global_sem:        # 拿不到就在这排队，源之间不再一齐冲出去
        await run_source(name, cfg, queue)

连接池：TCPConnector 把底层连接也限住

信号量管的是协程层面的"在途逻辑请求"，操作系统层面的 TCP 连接池还得单独限。我用 aiohttp 的连接器统一收口，避免连接数失控：

connector = aiohttp.TCPConnector(
    limit=50,              # 全局总在途连接上限
    limit_per_host=8,      # 单 host 在途连接，与 per-source 信号量对齐
    ttl_dns_cache=300,     # 缓存 DNS，别每个请求都解析一遍
)
sess = aiohttp.ClientSession(connector=connector,
                             timeout=aiohttp.ClientTimeout(total=10))

429/503：有限次指数退避 + jitter，绝不静默丢任务

这是被生产环境狠狠修过的一处。最早我被限流后 sleep 一下然后 return，注释还写着"任务还在队列里"——其实根本不在，任务就这样悄悄蒸发了。正确做法是在 crawl_one 内做有限次指数退避重试，带 jitter 避免所有 worker 同时醒过来再打一次；退避用完才把任务放回队尾，而不是吞掉：

import random

MAX_RETRIES = 3
BASE_BACKOFF = 1.0   # 秒，基数 1s -> 1s/2s/4s

async def crawl_one(name: str, cfg: dict, job: dict,
                   queue: asyncio.Queue) -> None:
    for attempt in range(MAX_RETRIES + 1):
        async with limiters[name]:           # 真正发请求才占信号量
            async with sess.get(job["url"]) as resp:
                if resp.status in (429, 503):
                    if attempt == MAX_RETRIES:
                        # 退避耗尽：放回队尾稍后再来，绝不静默 return
                        await queue.put(job)
                        return
                    # 指数退避 + jitter，错峰醒来
                    delay = BASE_BACKOFF * (2 ** attempt) + random.uniform(0, 0.5)
                    await asyncio.sleep(delay)
                    continue
                resp.raise_for_status()
                await parse_and_save(name, resp)
                return

放回队尾不等于无限循环——一条任务反复失败，最终会在 outbox 里累计失败次数并触发熔断进死信，这部分在看门狗那篇讲。

单源内 Queue 分发 + worker

每个源内部是标准的生产者—消费者：生产者把待抓 URL 填进队列，几个 worker 循环取任务。task_done() 必须放在 finally 里，否则任务一抛异常 queue.join() 就永远等下去：

async def fetch_worker(name: str, cfg: dict, queue: asyncio.Queue) -> None:
    while True:
        job = await queue.get()
        try:
            if job is None:        # 毒丸：缩容/停机时收到就退出
                return
            await crawl_one(name, cfg, job, queue)
        finally:
            queue.task_done()      # 无论成败都要标记

背压与热同步：有界队列 + 不重启改并发

队列设 maxsize=200，满了 put() 自然阻塞生产者，背压白送。改并发度不重启：起一个协程盯配置文件 mtime，变了就重载进共享字典；worker 数量随目标值伸缩——信号量大小改不了，所以扩容靠 create_task 补人、缩容靠多发毒丸让多余 worker 自然退出。完整细节见之前那篇讲并发与锁取舍的文章同类思路。

备选方案与权衡

我的选择备选为什么没选
进程内 Semaphore 限流全局限流网关 / 分布式令牌桶单进程部署，进程内信号量零依赖、足够；多实例才需要 Redis 令牌桶
有界队列反压无界队列 + 独立消费者无界队列在消费慢时会把内存撑爆，有界队列把节奏反过来压给生产者
自管协程池Celery / RQ 外部 worker采集是常驻长连接流，asyncio 协程比多进程 worker 更省资源；代价是故障恢复得自己写

核心经验：并发不是"开越多协程越快"，而是"全局控源数、单源控在途、队列做背压、配置在线可调"。两层信号量 + worker 不是重复造墙，而是分别兜住"对外礼貌"和"内部扇出"；429 退避必须有上限，退避用完放回队尾而不是吞掉任务——被生产环境教出来的细节，都是血泪。
