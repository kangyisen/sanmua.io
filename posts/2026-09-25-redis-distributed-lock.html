Redis 分布式锁在订单、积分、续期、背包里的真实用法

2026-09-25GoRedis

单机时代进程内的 mutex 就够了。但服务一旦多实例部署，或者同一用户手快点两次按钮，进程内锁立刻失效。这个项目里 Redis 分布式锁几乎贯穿所有写操作。这篇基于真实代码，讲清楚锁怎么实现、key 怎么设计、什么时候用阻塞锁，以及为什么锁之外还要数据库兜底。

锁的底层实现：SetNX + UUID + Lua 解锁

最朴素的加锁是 SetNX，但有两个经典坑必须处理：锁过期后被别人拿走、以及解锁时误删别人的锁。我们的实现给每把锁生成一个 UUID 作为持有者标识：

func (k *RedisCache) Lock(key string, expireTime ...time.Duration) (bool, error) {
    exp := 120 * time.Second
    if len(expireTime) > 0 { exp = expireTime[0] }
    value := uuid.New().String()
    ok, err := global.GVA_REDIS.SetNX(ctx, key, value, exp).Result()
    if ok { k.lockValues.Store(key, value) } // 记录本进程持有
    return ok, err
}

解锁用 Lua 脚本保证「判断 + 删除」原子，只有 key 的值等于自己的 UUID 才删，杜绝锁过期后误删新持有者的锁：

var unlockLuaScript = redis.NewScript(`
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
`)
func (k *RedisCache) Unlock(key string) error {
    value, ok := k.lockValues.Load(key)
    if !ok { return nil } // 没持有记录，安全忽略
    k.lockValues.Delete(key)
    return unlockLuaScript.Run(ctx, redis, []string{key}, value).Err()
}

阻塞锁 LockAndWait：愿意等的场景

Lock 抢不到立刻失败，但续期、扣积分这类场景，用户已经在等结果，直接报「操作太频繁」体验很差。于是有了自旋等待版，每 200ms 重试一次，直到拿到或超时：

func (k *RedisCache) LockAndWait(key string, expireTime time.Duration) (bool, error) {
    wait := 200 * time.Millisecond
    retryCnt := expireTime / wait
    for i := 0; i < int(retryCnt); i++ {
        value := uuid.New().String()
        ok, _ := redis.SetNX(ctx, key, value, expireTime).Result()
        if ok { k.lockValues.Store(key, value); return true, nil }
        time.Sleep(wait)
    }
    return false, nil
}

选择原则很简单：防重复提交（下单）用 Lock，抢不到说明用户重复点了，直接拒绝；串行化业务（续期 / 扣积分 / 用物品）用 LockAndWait，短暂排队后能成功。

真实锁点：粒度都锁到「用户 / 对象」

下单        order_create:{userId}              Lock     防重复下单
处理回调    order:handle:{orderId}             Lock     防回调并发处理
会员续期    membership:{appId}:{userId}        LockAndWait 防并发续期
积分扣减    points_consume:{appId}:{userId}    LockAndWait 防并发扣减 / 入账
使用背包    backpack_use:{userId}:{itemId}     LockAndWait 防重复使用

关键是锁的粒度足够细——锁到具体用户或具体对象，而不是锁全局。不同用户之间完全不竞争，并发才上得去。会员和积分锁还带了 appId，因为同一用户在不同产品下的账户是隔离的。

超时时间：统一 30 秒

业务锁统一传 30 秒（底层默认是 120 秒）。考量：

  • 太短：事务还没提交锁就自动释放，另一请求拿到锁，两个事务交错；
  • 太长：进程崩溃后，被锁 key 要等 30 秒才自动解开，用户会明显卡住。

业务事务都是数据库本地操作，正常几十毫秒，30 秒是「正常永远用不到、异常也能自愈」的折中。

unlock 时机：必须在事务提交之后

锁要覆盖整个事务，且释放晚于提交。否则锁先解、事务没落库，另一个请求拿到锁读不到刚写的数据。项目里的写法是先跑完事务，再用 defer 释放，保证「锁内事务一定先落库」：

locked, _ := cache.LockAndWait(lockKey, 30*time.Second)
if !locked { return errors2.ErrorFrequency }
defer cache.Unlock(lockKey)   // 函数返回（事务已提交）后才执行
return db().Transaction(func(tx *gorm.DB) error { ... })

Redis 6.0 兼容：被生产环境教出来的细节

线上是 Redis 6.x，几个 7.0 才有的命令会直接报错，代码里用 Lua 或老命令绕过：

  • EXPIRE key NX 需 7.0+，改用 Lua：仅当 key 存在且无 TTL（ttl == -1）时才设过期；
  • EXPIRETIME 需 7.0+，改用 PTTL 取剩余毫秒（不存在返回 -2，无 TTL 返回 -1）。
var expireNXScript = redis.NewScript(`
if redis.call("ttl", KEYS[1]) == -1 then
    return redis.call("expire", KEYS[1], ARGV[1])
end
return 0
`)

锁只是第一道防线，不是一致性的全部

网络分区、Redis 故障时锁可能失效，所以关键写操作都有数据库层兜底，这是最重要的认知：

场景锁负责数据库兜底
订单减少并发回调状态守卫 WHERE pay_status NOT IN 终态
积分串行化扣减乐观锁 version + 余额条件 WHERE 余额-冻结 >= ?
履约串行处理order_id 唯一索引 + 成功状态计数

以积分扣减为例，它是「分布式锁 + 乐观锁重试」双保险：外层锁把同一用户的请求串行，内层事务更新时带 WHERE id=? AND version=?，若这期间版本变了导致影响行数为 0，就重试最多 3 次：

for attempt := 0; attempt < 3; attempt++ {
    err = db().Transaction(func(tx *gorm.DB) error {
        return deductPointsCore(appId, userId, amount, recordType, tx)
    })
    if err == nil { return nil }
    if errors.Is(err, errPointsConcurrentConflict) { continue } // 版本冲突，重试
    return err
}
return errors2.ErrorSystemBusy

核心经验：分布式锁负责「减少冲突、提升吞吐」，数据库约束负责「最终正确」。锁会超时、会丢、会因网络分区失效，但唯一索引和条件更新不会骗你。永远别把锁当成一致性的唯一保障。
