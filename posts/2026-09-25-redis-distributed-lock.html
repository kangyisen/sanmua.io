Redis 分布式锁在订单、积分、续期里的五个应用场景

2026-09-25GoRedis

单机时代，进程内的互斥锁（mutex）就够了。但一旦服务多实例部署，或者同一用户并发点两次按钮，进程内锁就失效了。这个项目里 Redis 分布式锁几乎贯穿所有写操作，整理一下用到的地方和踩坑。

五个锁点

订单创建    lock order:{userId}         防同一用户重复下单
订单处理    lock order_handle:{orderId}  防支付回调并发处理
积分扣减    lock points_consume:{userId} 防并发扣减超扣
会员续期    lock membership:{userId}     防并发续期
背包使用    lock backpack:{itemId}        防重复使用物品

可以看到锁的粒度都很细：锁到具体用户或具体对象，而不是锁全局。这样不同用户之间完全不竞争，并发才上得去。

锁的参数怎么定

统一用 30 秒超时。这个值的考量：

  • 太短：业务事务还没跑完锁就自动释放了，另一个请求拿到锁，两个事务交错；
  • 太长：进程崩溃后，被锁的 key 要等 30 秒才自动解开，用户会卡住。

我们的业务事务都是数据库本地操作，正常几十毫秒，30 秒是「正常情况永远用不到、异常情况也能自己恢复」的折中。

最容易写错的一点：unlock 的时机

锁必须在事务提交之后才释放。反直觉的写法是这样：

// ❌ 错误：事务还没 commit 就 unlock
redis.Lock(key)
tx := db.Begin()
tx.Create(order)
tx.Commit()
redis.Unlock(key)   // commit 在 unlock 前，这个是对的

真正的坑在于用 defer redis.Unlock(key)——如果 defer 写在 tx.Commit() 之前，函数 return 时 defer 执行 unlock，但此时事务可能还没提交完，另一个请求拿到锁读不到刚写入的数据。我们的做法是把 defer unlock 放在事务提交之后的位置，保证「锁内事务一定先落库」。

锁只是第一道防线，不是全部

分布式锁能挡掉绝大多数并发，但网络分区、Redis 故障时锁可能失效。所以关键写操作还是要靠数据库层面的唯一约束 / 乐观锁 / 状态机兜底：

  • 订单：状态字段做条件更新（WHERE status = 'pending'），已处理的订单重复回调直接忽略；
  • 积分：扣减用 WHERE points >= ?，数据库层保证不扣成负数；
  • 履约：OrderFulfillment 有唯一约束，重复履约插不进去。

经验是：分布式锁负责「减少冲突」，数据库约束负责「最终正确」。别把锁当成一致性的唯一保障——锁会超时、会丢，但唯一索引不会骗你。
