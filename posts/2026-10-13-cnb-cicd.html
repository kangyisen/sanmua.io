CNB CI/CD：分环境部署、菜单同步与备份回滚

2026-10-13GoDocker架构

背景：两套环境，一条流水线

「一秒修图」后台基于 gin-vue-admin（GVA）二开，但线上并不是 GVA 那套 docker-compose 全家桶。真实拓扑是分裂的：日常开发跑在 123.57.222.105，前端是 1Panel 管理的静态站点（目录 /opt/1panel/www/sites/123.57.222.105/index），后端是一个叫 aizaotu-server 的 Docker 容器，监听 8889；生产跑在 114.215.189.118，前端是 /www/wwwroot/aizaotu/dist 的静态文件，后端是 systemd 服务 Zaotu 拉起的 Linux 静态二进制 main，监听 8888，对外域名 https://interface.zaotuai.cn。

所有自动化都收敛在仓库根目录的 .cnb.yml 里，跑在 CNB（cnb.build）上。这篇文章就拆开这份真实配置看：它怎么按改动范围决定部署动作、怎么把 develop 自动送进生产、怎么解决「后台菜单是运营在 develop 库里手改的」这个老问题，以及发版失败后怎么一把滚回去。

为什么要分环境、分动作

先想清楚三个约束，后面所有设计都是被它们逼出来的：

  • 前端和后端是两个互不相关的交付物。改一眼前端按钮，不值得重建并重启 Go 容器；反过来改一行 Go 代码，也不该把静态站点重新打一遍。所以 develop 的流水线必须按改动路径拆分。
  • 菜单数据会漂移。GVA 的后台菜单、权限、API、casbin 规则是数据库里的行数据，运营经常在 develop 后台页面上手工调整。如果发布只是把二进制换上去，生产库的菜单永远落后于 develop。
  • 配置和密钥不能进镜像。微信小程序密钥等 runtime 配置独立维护在服务器上，仓库里的 config.docker.yaml 缺少 business.wechat-app 段，绝不能拿它覆盖线上文件。同理，editor/ 是一个独立部署的子项目，发布包必须原样保留。

真实实现一：develop 流水线按改动范围分流

.cnb.yml 里 develop.push 下挂了三个任务。前两个用 ifModify 做条件触发：只有 web/** 变了才走前端构建，只有 server/** 变了才走后端容器重建：

develop:
  push:
    - name: 构建并部署开发环境后台
      ifModify:
        - ".cnb.yml"
        - "web/**"
      docker:
        image: node:22
      # npm install --legacy-peer-deps → npm run build
      # tar czf .cnb-release/aizaotu-web-develop.tar.gz -C web/dist .

    - name: 构建并部署开发环境后端
      ifModify:
        - ".cnb.yml"
        - "server/**"
      services:
        - docker
      docker:
        image: docker:27-cli
      # docker build -t aizaotu-server:develop server
      # docker save aizaotu-server:develop | gzip > .cnb-release/aizaotu-server-develop.tar.gz

后端任务在远端并不是盲目重启。它先做一道硬校验：线上必须存在 config.aizaotu-runtime.yaml，缺失就立刻终止，而且这条检查写在「停止旧服务」之前，避免服务停了又起不来：

test -s config.aizaotu-runtime.yaml || { echo 'Missing config.aizaotu-runtime.yaml; aborting deployment'; exit 1; }
python3 check_runtime_config.py config.aizaotu-runtime.yaml
# 业务容器与 redis 挂在同一个自定义网络 aizaotu-business
docker network inspect aizaotu-business >/dev/null 2>&1 || docker network create aizaotu-business
gunzip -c aizaotu-server-develop.tar.gz | docker load
docker run -d --name aizaotu-server --network aizaotu-business --restart always \
  -p 8889:8889 \
  -v "$REMOTE_APP_DIR/config.aizaotu-runtime.yaml:/go/src/.../config.docker.yaml:ro" \
  -v "$REMOTE_APP_DIR/uploads:.../uploads/file" \
  -v "$REMOTE_APP_DIR/log:.../log" \
  aizaotu-server:develop

前端任务则保留一个细节：解压前把 editor 目录改名藏起来，清完目录再挪回来，发布包永远碰不到这个独立项目。

真实实现二：每次 push develop，自动开一张到 master 的 MR

第三个 develop 任务不做部署，只做一件事：调用 CNB 开放 API，检查并创建 develop → master 的合并请求。它是幂等的——先拉 open 状态的 MR 列表，已存在就跳过；创建时若 API 返回「已存在/无差异」类错误（400/409/422）也视为正常：

const listUrl = `${apiBase}/${repoPath}/-/pulls?state=open&base_ref=${encodeURIComponent(targetBranch)}&page=1&page_size=50`;
const openPulls = await request(listUrl);
const existed = Array.isArray(openPulls) && openPulls.some((pull) =>
  normalizeRef(pull?.head?.ref) === sourceBranch &&
  normalizeRef(pull?.base?.ref) === targetBranch
);
if (existed) { console.log('已存在打开的合并请求，跳过创建。'); return; }
await request(`${apiBase}/${repoPath}/-/pulls`, {
  method: 'POST',
  body: JSON.stringify({ title: `从 ${sourceBranch} 合并到 ${targetBranch}`, head: sourceBranch, base: targetBranch, head_repo: repo })
});

这样工作流就闭环了：push develop → 自动部署开发环境 + 自动准备好一张待人工 Review 的 MR → 人在 CNB 上点合并，master 一收到 push（包括 MR 合入），生产部署立即触发。

真实实现三：生产部署，一个脚本锚点前后端共用

master.push 下也有两个任务，但部署逻辑用 YAML 锚点抽成了同一段。前端任务在 node:22 容器里构建 web/dist；后端任务在 golang:1.24-bookworm 里交叉编译两个产物——主程序和 cmd/menu-sync 这个小工具：

GOPROXY=https://goproxy.cn,direct CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -mod=mod -trimpath -ldflags="-s -w" -o ../.deploy_build/master-server/main .
go build -mod=mod -trimpath -ldflags="-s -w" -o ../.deploy_build/master-server/menu-sync ./cmd/menu-sync
# 两个任务的部署脚本共用同一段：
env:
  MASTER_DEPLOY_MODE: web
  MASTER_SSH_PASSWORD: &master_ssh_password '...'
script: &master_deploy |
  # ... 打包 → scp 到 mktemp -d /tmp/aizaotu-master.XXXXXXXX 暂存目录
  sshpass -e ssh "$DEST" bash -s -- "$MODE" "$REMOTE_TMP" ... <<'REMOTE'
  set -euo pipefail

真正的服务器端逻辑通过 bash -s 以 stdin 喂给生产机执行。它先取一把并发锁，再对「即将被替换的文件」做精确备份，然后才敢停服务：

backup_root="/www/wwwroot/aizaotu/.cnb-backups"
exec 9>"$backup_root/$mode.lock"
flock -w 600 9
backup="$backup_root/$(date -u +%Y%m%dT%H%M%S)-${stage##*/}-$mode.tar.gz"
# 只备份这次要替换的文件，resource、密钥等原样不动
find "$stage/unpacked" -type f -printf '%P\n' > "$stage/managed.txt"
tar czf "$backup" -C "$server_dir" -T "$stage/existing.txt"
rollback_needed=1
systemctl stop "$service"
"$stage/menu-sync" -config "$server_dir/config.yaml" -action backup -file "$menu_backup"
"$stage/menu-sync" -config "$server_dir/config.yaml" -action apply -file "$stage/menus.json"
cp -a "$stage/unpacked/." "$server_dir/"
chmod 755 "$server_dir/main"
systemctl start "$service"

服务起来后有两级健康检查：本机先轮询 30 次 http://127.0.0.1:8888/health 必须返回 200，再从公网打 https://interface.zaotuai.cn/api/health（带 --retry 3）确认链路通：

healthy=0
for attempt in {1..30}; do
  if systemctl is-active --quiet "$service" &&
     [[ "$(curl --max-time 5 -sS -o /dev/null -w '%{http_code}' http://127.0.0.1:8888/health)" == 200 ]]; then
    healthy=1; break
  fi
  sleep 2
done
[[ "$healthy" == 1 ]] || { echo "Backend health check failed" >&2; exit 1; }
[[ "$(curl --retry 3 --retry-delay 2 --max-time 15 -sS -o /dev/null -w '%{http_code}' "$site_url/api/health")" == 200 ]]

真实实现四：menu-sync——把 develop 的菜单快照带到生产

生产后端任务打包前会先跑 scripts/export-develop-menus.sh：它 SSH 到开发机，把刚编译好的 menu-sync 二进制 docker cp 进 aizaotu-server 容器，在容器里用 develop 的 runtime 配置只读导出一份菜单快照。注意脚本头注释写得很直白：Export using develop's mounted runtime config and Docker network. No DB writes.

docker exec -w "$workdir" "$container" "$stage/menu-sync" \
  -config config.docker.yaml -action export -file "$stage/menus.json"
docker cp "$container:$stage/menus.json" "$stage/menus.json"

menu-sync 是 server/cmd/menu-sync/main.go 里一个独立小工具，四个动作 export / apply / backup / restore。它没有任何 schema migration，连接前先校验运行配置是标准 MySQL，并强制要求八张菜单/权限/策略表全部存在且是 InnoDB（因为 apply 要靠事务保证原子性）：

action := flag.String("action", "", "export, apply, backup, or restore")
connection.SetMaxOpenConns(1)
db.Raw(`SELECT COUNT(*) FROM information_schema.tables WHERE table_schema = DATABASE()
  AND table_name IN ('sys_base_menus','sys_base_menu_parameters','sys_base_menu_btns',
    'sys_authority_menus','sys_authority_btns','sys_authorities','sys_apis','casbin_rule')
  AND engine = 'InnoDB'`).Scan(&count)
if count != 8 { return fmt.Errorf("all eight menu/role/API/policy tables must exist and use InnoDB") }

发布顺序因此是：先 -action backup 把生产当前菜单存成 .menus.json 兄弟文件，再 -action apply 写入 develop 导出的快照。工具写文件用的是 O_EXCL，拒绝覆盖上一次部署留下的备份，回滚链路才不会断。

真实实现五：失败回滚靠一个 EXIT trap

回滚逻辑是远端脚本里的一个 rollback()，挂在 trap ... EXIT 上。只有当脚本以非零状态退出、且 rollback_needed=1（即已经越过「备份完成、开始替换」那一步）时才触发：停服务、按 managed.txt 删掉这次新写入的文件、解开备份 tar 还原、若菜单也动过就用 -action restore 把 .menus.json 灌回去，最后重新 systemctl start：

rollback() {
  status=$?
  trap - EXIT
  if (( status != 0 && rollback_needed )); then
    systemctl stop "$service"
    while IFS= read -r file; do rm -f -- "$server_dir/$file"; done < "$stage/managed.txt"
    tar xzf "$backup" -C "$server_dir"
    if (( menu_restore_needed )); then
      "$stage/menu-sync" -config "$server_dir/config.yaml" -action restore -file "$menu_backup"
    fi
    systemctl start "$service"
  fi
  exit "$status"
}
trap rollback EXIT

前端模式的回滚更简单：备份时 tar czf "$backup" --exclude='./editor'，失败就清空 web_dir（同样跳过 editor）再解开备份。整套机制意味着：发版失败的默认动作是「回到发版前那一秒」，而不是挂在原地等人救。

镜像与 Nginx：开发走容器，生产走裸二进制

开发环境的镜像就是 server/Dockerfile：多阶段构建，golang:alpine 编译后丢进 alpine:latest，设 TZ=Asia/Shanghai，EXPOSE 8889，入口 ./server -c config.docker.yaml——而这个 config.docker.yaml 在运行时被宿主机的 runtime 配置只读挂载覆盖。仓库里 deploy/docker/Dockerfile（centos:7 里同时跑 mysqld、redis、nginx 的 all-in-one）和 docker-compose.yaml（gva-web/gva-server/gva-mysql 那套）其实是 GVA 上游遗留，真实生产早已不用，只留作本地开发参考。

生产 Nginx（nginx.conf）本身不参与部署流程——流水线明确不碰它。要点只有几个：静态根 /www/wwwroot/aizaotu/dist，/api/ 反代到 127.0.0.1:8888，且 proxy_pass 结尾的 / 用来做前缀剥离，配置里专门注释警告不要加 rewrite ... break（会和 location 内的 if 一起搞乱捕获组，导致 404）；OPTIONS 直接回 204；长连接业务把 proxy_read_timeout 放到 86400s：

location /api/ {
    if ($request_method = 'OPTIONS') { return 204; }
    proxy_pass http://127.0.0.1:8888/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400s;
}

权衡与取舍

  • 密码直接写进 .cnb.yml。开发机密码、生产密码都明文在仓库里，靠仓库私有和 CNB 环境变量兜底；好处是 YAML 锚点 &master_ssh_password 让前后端任务天然复用同一份配置，不用维护外部密钥系统。这是小团队用复杂度换运维负担的典型选择。
  • 双轨部署。开发用 Docker 容器（docker save | scp | docker load，简单但吃带宽），生产用交叉编译静态二进制 + systemd（Zaotu.service，User=www，Restart=on-failure）。两套运行时不统一，但生产机上没有 Docker 依赖、健康检查可以直接 curl 127.0.0.1:8888/health，排障路径最短。
  • 备份是「精确替换集」而不是整机快照。managed.txt 只记录这次会被覆盖的文件，备份小、回滚快，代价是脚本必须自己维护清单；菜单快照和文件备份成对出现（.tar.gz + .menus.json），任何一半缺失都不会假装成功。
  • flock -w 600 串行化发布。前后端共用同一个备份根目录，用一把文件锁避免两次发布交错备份/回滚，最多等 10 分钟，宁可排队也不并发改生产。

CI/CD 的价值不在于「点一下按钮就发版」，而在于把发版拆成可证明安全的步骤：先按改动范围少做事，再在停服前备份、健康检查后才宣布成功、失败时由 trap 自动退回到上一秒。菜单会漂移、密钥不能进镜像、editor 不能被覆盖——这些脏约束，最终都变成了 .cnb.yml 里一行行可以被 Review 的 shell。
