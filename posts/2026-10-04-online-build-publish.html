AI 游戏工程的在线构建、发布与权限设计

2026-10-04Go架构编程

除了面向 C 端的 App，我还参与了 Lunetale 的 B 端管理后台 OpenGame：AI 游戏工程生成、在线构建与发布、模型中心、订单积分、数据看板都在这一侧。后台一多，最先头疼的就是两件事：构建这条异步链路怎么不卡死、不变成僵尸任务，以及权限怎么落到后端而不是只藏菜单。这篇讲我怎么用 JWT 加 Casbin 把权限粒度做到接口，以及构建任务怎么真正跑起来。整体架构背景见双服务架构。

在线构建：先把它想成一个状态机

用户点「构建发布」，后端生成一个构建任务丢给 worker 异步跑。慢操作绝不同步等。任务用状态机管起来，非法跳转直接拒绝——比如构建中不能跳回待构建：

const (
    BuildPending = "pending"
    BuildRunning = "running"
    BuildSuccess = "success"
    BuildFailed  = "failed"
)

func (t *BuildTask) Transit(next string) error {
    allowed := map[string][]string{
        BuildPending: {BuildRunning, BuildFailed},
        BuildRunning:  {BuildSuccess, BuildFailed},
    }
    for _, s := range allowed[t.Status] {
        if s == next {
            t.Status = next
            return nil
        }
    }
    return errIllegalTransition
}

worker 怎么真正跑构建：逐行回传日志

状态机只是门面，真正干活的是 worker。它用容器跑构建脚本，逐行读 stdout/stderr 写进日志表或经 WebSocket 推给前端，用户在页面上能看到构建实时滚动：

后台点"构建"
   -> 生成 BuildTask(pending)
   -> worker 取任务, 占并发槽(running)
   -> docker run ./build.sh 逐行回日志
   -> success / failed
   -> 成功产物传七牛云, 状态置可发布
func (w *Worker) runBuild(ctx context.Context, task *BuildTask) error {
    cmd := exec.CommandContext(ctx, "docker", "run", "--rm", buildImage, "./build.sh")
    stdout, _ := cmd.StdoutPipe()
    cmd.Stderr = cmd.Stdout // 合并错误流，一起抓日志
    if err := cmd.Start(); err != nil {
        return err
    }
    scanner := bufio.NewScanner(stdout)
    for scanner.Scan() {
        w.appendLog(task.ID, scanner.Text()) // 写日志表 / WS 推前端
    }
    return cmd.Wait()
}

并发控制、取消与僵尸任务兜底

构建很吃资源，worker 用一个带缓冲的信号量限制并发（默认 4 路）；前端点取消就调任务上挂的取消函数。最棘手的是 worker 宕机——任务卡在 running 永远不动，所以要有定时兜底把超时的僵尸任务判成 failed：

var sem = make(chan struct{}, 4) // 最多同时跑 4 个构建

func (w *Worker) schedule(task *BuildTask) {
    sem <- struct{}{}        // 占一个槽
    defer func() { <-sem }() // 跑完释放
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Minute)
    defer cancel()
    task.refCancel = cancel // 前端点取消时调用
    w.runBuild(ctx, task)
}

// 定时兜底：worker 宕机后卡在 running 的任务，判成 failed
func SweepZombieBuilds() {
    db.Model(&BuildTask{}).
        Where("status = ? AND updated_at < ?", "running", time.Now().Add(15*time.Minute)).
        Update("status", "failed")
}

工程生成：模板加参数，不现场写代码

新建工程不是从零生成，而是套预置模板再填参数：项目名、用到的模型、主题色、入口场景。后端把模板拷一份、替换占位符，就成了一个可构建的工程目录，构建脚本不用每个项目单独适配。

JWT 鉴权：剥掉 Bearer 前缀

后台登录后发 JWT，中间件统一校验。这里有个容易漏的细节：前端一般传 Authorization: Bearer <token>，验签前必须把 Bearer 前缀剥掉，否则带前缀的字符串直接拿去解析必然失败：

func AuthRequired() gin.HandlerFunc {
    return func(c *gin.Context) {
        h := c.GetHeader("Authorization")
        token := strings.TrimPrefix(h, "Bearer ") // 剥前缀，否则验签失败
        claims, err := jwt.Parse(token)
        if err != nil {
            c.AbortWithStatusJSON(401, gin.H{"error": "unauthorized"})
            return
        }
        c.Set("userID", claims.UserID)
        c.Next()
    }
}

Casbin：策略挂角色，用 g 做用户继承

标准做法是 sub 存用户 ID，策略只挂角色，用户和角色的关系用 g 表继承。这样加权限只动角色，不用给每个用户单独配策略：

// 策略(p)挂角色；用户-角色继承(g)
// p, editor, /api/projects, READ
// p, admin,  /api/build,    *
// g, alice,  editor   <- 用户 alice 继承 editor 角色

func RequirePermission(obj, act string) gin.HandlerFunc {
    return func(c *gin.Context) {
        sub := c.GetString("userID") // sub 是用户 ID
        ok, err := enforcer.Enforce(sub, obj, act)
        if err != nil || !ok {
            c.AbortWithStatusJSON(403, gin.H{"error": "forbidden"})
            return
        }
        c.Next()
    }
}

一个用户可以有多条 g（比如同时是 editor 和 admin），Casbin 的 Enforce 会沿角色继承反查，任一角色命中该接口即放行。菜单资源与接口用同一套 obj，前端按它渲染可见菜单，后端按它放行请求，两边不会对不上。

备选方案：在线构建 vs 接 CI

  • 接现成 CI：要维护外部系统、回传日志链路长，权限和任务状态不好控；
  • 自托管 worker + 容器：任务状态、日志、取消都在自己手里，代价是要自己扛并发和僵尸兜底；
  • 云构建服务：省运维，但构建资源和计费不透明，海外分发场景下我们选自托管。

构建产物传七牛云，构建机上不留大文件。配套的订单积分与支付履约见支付履约，并发写的一致性兜底见分布式锁。

核心经验：JWT 负责「你是谁」，Casbin 负责「你能做什么」，策略挂角色、用户用 g 继承。在线构建本质是个异步状态机，慢操作一律任务化，配合信号量并发上限、context 取消和僵尸任务定时兜底；权限必须落到后端接口，前端显示只是顺带。加角色、开菜单因此成了配置问题，而不是开发任务。
