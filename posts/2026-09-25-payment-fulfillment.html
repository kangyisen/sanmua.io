多渠道支付回调与幂等履约：订单管线设计笔记

2026-09-25Go支付

平台同时接了微信支付、支付宝，以及 Apple / Google 的应用内购买与订阅。支付是最不能出错的环节：钱收了权益没到、回调重复发、并发下单，任何一个都是真金白银。这篇基于真实代码，把下单、两类回调、订单状态机、两级幂等、策略模式履约完整拆开。

整条链路

用户下单  order_create.go   分布式锁 + 事务写 Order / OrderProduct
   ↓
支付回调  callback/         验签、校金额
   ↓       ↓           ↓             ↓
 微信    支付宝      Apple 订阅     Google 订阅
 服务端   服务端      服务端通知      Pub/Sub push
   ↓
订单处理  order_handle.go   锁 + 终态判断 + 状态守卫
   ↓
自动履约  fulfillment/      两级幂等 + 策略模式分发

下单：锁内事务，预付放事务外

CreateOrder 先用 order_create:{userId} 锁防同一用户重复提交，然后在事务里写订单和订单产品，ID 用 Snowflake 生成：

success, err := cache.Lock(fmt.Sprintf("order_create:%d", form.UserId), 30*time.Second)
if err != nil || !success { return resp, errors2.ErrorFrequency }
defer cache.Unlock(lockKey)

order.ID = datatype.GenerateID()
err = db().Transaction(func(tx *gorm.DB) error {
    if call != nil { if err := call(tx, order, op); err != nil { return err } }
    if err := tx.Create(order).Error; err != nil { return errors2.ErrorInternal }
    return tx.Create(op).Error
})

事务支持一个 BizOrderCallback 钩子，让不同业务在下单时夹带额外写入。调起第三方预付（PrePay）刻意放在事务之外——第三方接口耗时不可控，放进事务会长时间占着 DB 连接；预付失败则把订单标记为失败，保留记录便于排查。

回调分两类，鉴权方式根本不同

  • 服务端回调（微信、支付宝、Apple/Google 订阅通知）：支付平台直接请求我们服务器，必须验证签名并解密，回调字段一律不可信；
  • 客户端回调（Apple Pay、Google Pay 一次性购买）：App 端发请求，用户可控，必须校验 ctx.UserId == order.UserId，并把支付凭证拿去向苹果 / 谷歌二次验证。

Apple 客户端回调：一条完整的校验链

这是防薅羊毛的核心。支付成功时不是客户端说付了就算，而是拿着交易号向苹果服务端复查，然后逐项校验：

exp = http.CheckToken(ctx)                       // 1. 必须登录
resp, err := applePayer.GetAppStoreOrder(req.AppleOrderId) // 2. 向苹果复查
if resp.Environment == "Sandbox" && !conf.IsSandbox { ... } // 3. 沙盒回退（审核/TestFlight）
if resp.PurchaseDate/1000 < time.Now().Unix()-86400 { ... } // 4. 购买超 24h，拒绝（防历史订单重放）
if resp.BundleId != conf.BundleId { ... }        // 5. BundleId 必须匹配
order, _ := order2.GetOrderFirstProduct(req.OrderId, ctx.UserId()) // 6. 带 userId 查订单
if order.UserId != ctx.UserId() { ... }          // 7. 校验所有权
if resp.ProductId != order.ThirdProductId { ... }// 8. 商品必须匹配

这里有个很真实的细节——金额怎么处理。App Store 内购价格由 App Store Connect 强制收取、客户端无法篡改，苹果返回的 price 才是权威实付；而我们后端商品目录当时对所有商品用的是占位价 1000，并不是真实期望价。如果机械地「金额相等才放行」，所有内购都会被误判。所以 Apple 渠道是「以苹果价格为准，不一致就回写校正订单，再放行」：

if resp.Price > 0 && datatype.Amount(resp.Price) != order.RealPrice {
    db().Model(&business.Order{}).Where("id = ?", id).
        Update("real_price", datatype.Amount(resp.Price))
}

另外，非成功状态（取消 / 失败）的回调也必须校验订单所有权，否则有人能把任意订单标记成失败。

微信服务端回调：验签 + 金额严格相等

微信走的是服务端通知，先 ParseNotifyData 验签解密，再按 trade_state 映射状态：

err = payer.ParseNotifyData(ctx.Request, &result) // 验签 + 解密
if err != nil { return errors2.ErrorSecurityVerifySignError }

switch result.TradeState {
case "SUCCESS":     payStatus = enums.PayStatusSuccess
case "CLOSED","NOTPAY": payStatus = enums.PayStatusCancel
case "USERPAYING":  payStatus = enums.PayStatusWait
}
// 金额严格校验：≤0 异常，且必须与订单实付完全相等
if result.Amount.Total <= 0 { return errors.New("回调金额异常") }
if datatype.Amount(result.Amount.Total) != orderInfo.RealPrice {
    return errors.New("支付金额不匹配")
}

和 Apple 相反，微信渠道金额是严格相等、不等直接拒绝。差异来自价格的 source of truth 不同：微信订单金额是我们自己下单时定的，回调金额必须等于它；Apple 内购金额由商店定、后端只是占位价。

微信的响应协议也有讲究：处理成功必须回 {"code":"SUCCESS"}，否则微信会持续重推。所以遇到「订单已处理」（OrderRepeatHandle）也回 SUCCESS，让微信停止重试；而支付成功但我们内部处理失败时，要回 500 让微信稍后重推，不能丢单。

订单状态机与懒超时

订单有 5 个状态：1 等待 / 2 取消 / 3 失败 / 4 成功 / 5 超时。超时不是靠定时任务扫，而是在模型的 AfterFind 钩子中「懒处理」：查询到等待支付且创建已过 30 分钟的订单，就地转成超时，并用条件更新兜底：

func (o *Order) AfterFind(db *gorm.DB) error {
    if o.PayStatus == PayStatusWait &&
       o.CreatedAt.Add(30*time.Minute).Before(time.Now()) {
        o.PayStatus = PayStatusTimeout
        db.Transaction(func(tx *gorm.DB) error {
            // 再次条件更新，防并发重复改
            tx.Model(OrderModel).Where("id = ? AND pay_status = ?", o.ID, PayStatusWait).
                Update("pay_status", PayStatusTimeout)
            return nil
        })
    }
    return nil
}

订单处理：锁 + 终态判断 + 状态守卫

HandleOrderResult 用 order:handle:{orderId} 锁串行化，先查订单，已是终态（IsEnd）直接返回 OrderRepeatHandle，这是回调幂等的第一道：

locked, _ := cache.Lock(fmt.Sprintf("order:handle:%d", orderId), 30*time.Second)
defer cache.Unlock(lockKey)
order, _ := GetOrderBaseById(orderId)
if order.PayStatus.IsEnd() { return errors2.NewError(errors2.OrderRepeatHandle) }

状态更新 UpdateOrderStatus 在 SQL 层加了「状态守卫」，只允许从非终态更新，影响行数为 0 就安全忽略：

tx := db().Where("id = ? AND pay_status NOT IN ?", orderId,
    []PayStatus{Success, Fail, Cancel}).Updates(updateModel)
if tx.RowsAffected == 0 { return nil } // 已终态，幂等忽略

注意函数注释明确写了：本函数不校验订单归属，调用方必须先验，防止有人用别人订单号回调。

两级幂等：订单级 + 交易级

履约引擎 AutoFulfill 做了两层去重，这是踩过坑后补的：

订单级：查 OrderFulfillment 是否已有该订单的成功记录，有则拒绝：

tx.Model(fulfillmentModel).
    Where("order_id = ? AND status = ?", orderId, FulfillStatusSuccess).Count(&count)
if count > 0 { return errors2.ErrorOrderIdempotentReject }

交易级：订单级只按 orderId 去重，挡不住「同一笔商店交易被 StoreKit 重放 / 客户端重复下单生成了新订单」。所以再按商店交易号（Apple transactionId / Google purchaseToken，存在 OrderProduct.ThirdOrderId）兜底：

// 找出携带同一商店交易号的其它订单，看是否已成功履约
tx.Model(&OrderProduct{}).
    Where("third_order_id = ? AND order_id <> ?", storeTxId, orderId).Pluck("order_id", &ids)
tx.Model(fulfillmentModel).Where("order_id IN ? AND status = ?", ids, Success).Count(&count)
if count > 0 { return errors2.ErrorOrderIdempotentReject }

返回幂等拒绝时，客户端会把它当作「权益已发放」并结束掉那笔被重放的僵尸交易，既不重复发货，也清理了脏交易。

履约状态机 + 策略模式

履约记录有 Processing → Success / Failed 的状态：先记录开始，执行失败则置 Failed（不影响后续补发），成功置 Success。五种产品形态用策略接口分发：

type Fulfiller interface {
    Fulfill(op *business.OrderProduct, payChannel enums.PayChannel, tx *gorm.DB) error
}
func getFulfiller(t enums.ProductType) Fulfiller {
    switch t {
    case Subscribe, MembershipSubscription: return &subscriptionFulfiller{}
    case MembershipOnetime:                 return &membershipOnetimeFulfiller{}
    case CreditBoost:                       return &creditBoostFulfiller{}
    case BlindBox:                          return &blindBoxFulfiller{}
    case ChatPass:                          return &chatPassFulfiller{}
    }
}

每个履约器第一步都是「反查套餐配置」。这里有个防发错货的细节：反查要同时按 appId + 商店商品 ID + 平台（Apple/Google），因为 Apple 和 Google 可能存在同名 SKU，只按商品 ID 查会互相遮蔽：

platform := subscribe.PlatformFromPayChannel(payChannel)
pkg, err := subscribe.GetPackageByStoreProductId(op.AppId, op.ThirdProductId, platform, tx)

各履约器的去向：订阅 / 单次会员 → ExtendMembership（订阅给 Gold 等级，单次给 Silver）；加油包 → PointsIncome 入加油包账户；盲盒 / 畅聊卡 → 放进背包，由用户手动激活。会员来源（Apple 订阅 / Google 订阅 / 微信单次 / 支付宝单次…）由支付渠道推断并落库，便于后续对账。

内存商品目录

product_catalog.go 用 sync.Once 初始化只读注册表：productCatalogMap（内部 ID → 商品）和 storeProductLookupMap（Apple/Google 商店 ID → 商品，供履约反查）。每个商品含各商店 ID、价格、本地化展示字段（标题 / 副标题 / 角标 / 图片）、排序、以及类型特有元数据（DurationDays / DurationHours / CreditAmount / BoxType）。目录按 appId 过滤、按平台区分（Google 暂不返回盲盒与畅聊卡），商店是价格的唯一事实来源。

支付系统的目标其实就一句话：无论回调来几次、乱序来、重复来，最终结果都和「来一次」完全一样。订单 / 履约状态机 + 分布式锁 + 两级幂等 + 履约快照凑齐，基本就稳了；而不同渠道「金额严格还是校正」这种差异，必须顺着各自的事实来源来，不能一刀切。
