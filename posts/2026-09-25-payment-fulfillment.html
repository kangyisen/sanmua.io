多渠道支付回调与幂等履约：订单管线设计笔记

2026-09-25Go支付

平台同时接了微信支付、支付宝，以及 Apple / Google 的应用内购买和订阅。支付是最不能出错的环节——钱收了但权益没到、回调重复发、并发下单，任何一个出问题都是真金白银。这篇记录订单管线是怎么设计的。

整条链路

用户下单  →  order_create.go（分布式锁 + 事务）
    ↓
支付回调  →  callback/（验签、校金额）
    ↓        ↓            ↓              ↓
  微信    支付宝       Apple 订阅       Google 订阅
  服务端回调 服务端回调   服务端通知       Pub/Sub push
    ↓
订单处理  →  order_handle.go（HandleOrderResult，幂等检查）
    ↓
自动履约  →  fulfillment/（策略模式，按产品类型分发）

回调分两类，鉴权方式不同

这是最关键的一个区分：

  • 服务端回调（微信、支付宝、Apple/Google 订阅通知）：支付平台直接请求我们的服务器，我们必须验证签名，不能信回调里的任何字段；
  • 客户端回调（Apple Pay、Google Pay 一次性购买）：是 App 端发请求告诉我们「我付好了」，这种请求用户可控，所以必须校验 ctx.UserId == order.UserId，防止有人伪造别人的订单号来薅会员。

幂等：防的是「回调重复」

支付平台的回调机制是「没收到 200 就一直重发」。所以同一个回调可能来十次。我们的应对是：订单本身有状态机，处理前先看状态。

关键模型：

  • Order：订单主表，带支付状态，30 分钟未支付自动超时；
  • OrderProduct：下单时存产品快照，避免商品后续改价影响历史订单；
  • OrderFulfillment：履约状态，这是幂等的关键——已经履约过的请求直接返回成功，不重复发权益。

下单时用 order:{userId} 分布式锁防重复提交；处理回调时用 order_handle:{orderId} 锁，保证同一订单不会被两个回调并发处理。

履约：策略模式按产品类型分发

我们卖的东西形态差别很大：订阅会员、单次会员、积分加油包、盲盒、畅聊卡。履约逻辑如果都堆在一个函数里会变成巨大的 switch-case。于是抽成了策略：

func getFulfiller(productType ProductType) Fulfiller {
    switch productType {
    case ProductTypeSubscribe, MembershipSubscription:
        return subscriptionFulfiller{}
    case ProductTypeMembershipOnetime:
        return membershipOnetimeFulfiller{}
    case ProductTypeCreditBoost:
        return creditBoostFulfiller{}
    case ProductTypeBlindBox:
        return blindBoxFulfiller{}   // 放进背包
    case ProductTypeChatPass:
        return chatPassFulfiller{}    // 放进背包
    }
}

每个履约器只关心「怎么把权益给到用户」。新上一种产品，只要加一个 fulfiller 和一个 case，老代码一行不动。

几个踩过的坑

  • 金额校验不能省：回调里带的金额必须和本地订单金额比对一致才放行，否则改价/作弊订单会被放过。
  • 客户端回调也要验签：虽然校验了 UserId，但支付凭证（Apple/Google 的 receipt）要拿去向苹果/谷歌服务端二次验证，不能只看 App 传的布尔值。
  • 事务里别做外部调用：支付回调处理在数据库事务内，绝不在事务里请求 Apple/Google 服务器查收据——慢查询会把连接池打满。先验签入库，再异步补查。

支付系统的设计目标其实就一个：无论回调来几次、乱序来、重复来，最终结果都和「来一次」一样。幂等状态机 + 分布式锁 + 履约快照，三件套凑齐，基本就稳了。
