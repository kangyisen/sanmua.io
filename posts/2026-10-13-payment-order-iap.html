支付与订单：多渠道回调、Apple IAP 与订阅

2026-10-13Go支付架构

「一秒修图」是个 iOS + 安卓双端的 AI 修图 App，收钱这件事天然要接三条完全不同的通道：微信支付（APP 支付 + 扫码）、支付宝（APP 支付 + H5 网页支付），以及 Apple 内购。三家的下单协议、回调方式、验签算法、状态机都不一样，苹果这边还叠了一层自动续订订阅和 App Store Server Notifications V2。这篇复盘把 service/business/ 下 pay / order / callback / appstore 四个包里真实的下单抽象、回调验签、幂等与订阅处理完整记录下来。

背景：三种通道，三种世界

最开始的写法是在下单接口里 if payType == 微信 ... else if 支付宝 ... else if 苹果 ...，回调更是每个渠道一坨。三个渠道的差异远不止 SDK：微信 APIv3 要求下载平台证书、用 SHA256-RSA 验签；支付宝是表单回调、用平台公钥验签；苹果根本没有「服务端回调」——早期版本是 App 端支付完再通知服务端，服务端拿订单号去 App Store Server API 反查，后来才补上苹果服务器 V2 通知。如果抽象不做对，每加一个渠道就是一次全身手术。

统一抽象：一个 Payer 接口，三个适配器

最终落点是 service/business/pay/pay.go 里一个很薄的接口：下单方只认识 Payer，不认识任何具体渠道。

// service/business/pay/pay.go
type Payer interface {
    // Init 完成支付客户端初始化
    init() error

    // PrePay 根据系统订单生成预支付单，并生成APP端支付调起参数
    PrePay(*PrePayReq, enums.PayType) (map[string]string, error)

    // QueryOrderStatus 查询订单状态
    QueryOrderStatus(mechId string, tradeNo string, payType enums.PayType) (enums.PayStatus, string, error)
}

func GetPayer(payType enums.PayType) (payer Payer, err error) {
    idx := payType-1
    payer = payers[idx]
    if payer != nil { return payer, nil }
    // ... payerLocker 双检锁省略
    switch payType {
    case enums.PayTypeWechat, enums.PayTypeWechatQrCode:
        payer = newWechatPay()
    case enums.PayTypeApple:
        payer = newApplePay()
    case enums.PayTypeAliPay, enums.PayTypeAliH5Qrcode:
        payer = newAliPay()
    default:
        return nil, errors.New("不支持的支付类型")
    }
    if err = payer.init(); err != nil { return nil, err }
    payers[idx] = payer
    return payer, nil
}

几个值得记的设计决策：第一，payer 按 payType-1 做下标放进一个切片 payers，懒加载 + 双检锁，客户端第一次用到某个渠道才初始化证书；第二，PrePayReq 只有订单号、用户号、金额、备注、openId 这些各渠道都共有的字段，渠道差异藏在 PrePay 返回的 map[string]string 里——微信返回调起参数（appid/prepayid/sign），支付宝返回一串签名后的 order string，苹果只回 orderId/amount/currency，让 App 自己弹系统支付面板。

定价也按渠道拆。order/buy_goods.go 的 Buy() 里有段注释说得很直白：安卓/微信/支付宝以 b_android_package 为准，苹果成交价由 App Store 价格点决定，以 b_ios_subscription / b_ios_in_app_purchase 为准，「苹果侧不存在后台折扣」。下单成功后统一走 order_handle.go 的 WithBuyOrder：先对用户加分布式锁，事务里建一张 pay_status = PayStatusWait 的订单，事务外再调 payer.PrePay（第三方调用不可控，不能放在事务里）。

回调：三条独立路由，验签各做各的

先说一个诚实的结论：callback 包里并没有一个「根据请求识别渠道再分发」的中心 dispatcher——callback_base.go 里就两个公共函数 log() 和 db()。真实做法是一个渠道一条独立路由，handler 内部各自 pay.GetPayer 拿回对应 payer 做类型断言，验签不过直接返回失败让平台重试。

微信回调 WechatPayNotifyHandler 走 APIv3 的 ParseNotifyRequest，验签 + 解密一把完成，失败统一报「验证签名失败」：

// pay/pay_wechat.go：用证书下载器建验签器，验签并解密通知
verifier := verifiers.NewSHA256WithRSAVerifier(w.certDownloader)
handler, err := notify.NewRSANotifyHandler(w.conf.ApiV3Key, verifier)
// ...
_, err = handler.ParseNotifyRequest(context.Background(), request, notifyData)
if err != nil { return errors.New("验证签名失败") }

支付宝回调是表单，验签之外还多一步「这个通知是不是发给我们这个 AppID 的」，防止别的商户的回调打到我们这儿：

// callback/callback_pay_ali.go
err = payer.VerifySign(values)            // 平台公钥验签
if err != nil { exp = err; return }
if notifyData["app_id"] != conf.AppID {
    exp = errors.New("验证app_id失败，app_id不匹配")   // 防跨商户伪造
    return
}
if notifyData["trade_status"] == "TRADE_SUCCESS" {
    payStatus = enums.PayStatusSuccess
    orderId, _ = strconv.ParseInt(notifyData["out_trade_no"], 10, 64)
}
err = order.HandleOrderResult(datatype.SfID(orderId), payStatus, notifyData["trade_status"])

苹果最特殊：ApplyPayNotifyHandler 开头先 http.CheckToken(ctx)——因为它是 App 端回调而不是苹果服务器直推，必须鉴权；只有 PayStatus == PayStatusSuccess 时才真正去苹果那边反查订单，并连做四道校验：

// callback/callback_pay_apple.go
resp, err := payer.GetAppStoreOrder(notifyData.AppleOrderId)  // JWS 验签在内部
if resp.PurchaseDate < time.Now().Unix()-24*60*60 {
    return fmt.Errorf("订单已过期")        // 防拿历史订单恶意回调
} else if resp.BundleId != conf.BundleId {
    return fmt.Errorf("应用Bundle不匹配")
}
if resp.ProductId != order.ProductId {
    return fmt.Errorf("商品与订单不匹配")   // 不能把 A 套餐的单付到 B 订单上
}
// 全局幂等：一笔苹果交易只允许入账一次
if paid, ok := order2.FindPaidOrderByAppleTransaction(txnId); ok && paid.OrderId != notifyData.OrderId {
    return fmt.Errorf("该苹果交易已完成入账")
}

幂等：数据库条件更新才是闸门

所有渠道回调最后都汇到 order_handle.go 的 HandleOrderResult。它的幂等设计值得单独讲：真正的防重不是 Redis 锁（注释里明说锁只是「尽力而为」的优化层），而是一句带状态条件的 UPDATE——

// order/order_handle.go：只有「待支付」订单才能被翻成成功，并发下靠 InnoDB 行锁串行化
res := tx.Model(&business.Order{}).
    Where("order_id = ? AND pay_status = ?", orderId, enums.PayStatusWait).
    Update("pay_status", status)
if res.RowsAffected == 0 {
    // 已被其它回调处理过（重复/并发），幂等跳过，绝不重复发放
    return nil
}
return UpdateUserPointsByOrder(tx, &order)

重复回调时只有第一笔 UPDATE 命中 RowsAffected==1，后面的全命中 0 行直接返回 nil——对平台回 nil 是为了让它收到成功响应、停止重试。苹果侧再加一道交易级去重：order/apple_transaction.go 里 FindPaidOrderByAppleTransaction 按 apple_order_id + pay_status=成功 查，登录回调、匿名验证、续费通知四条通道发放前都先过它，保证同一笔交易全局只入一次账。

Apple IAP：JWS 证书链校验与双环境 fallback

苹果反查走 App Store Server API：pay_apple.go 用 .p8 私钥签 ES256 JWT 当 Bearer Token（aud 固定 appstoreconnect-v1），GET /inApps/v1/transactions/{orderId}。返回体里交易信息是一段 JWS，服务端手工验整条证书链——这是整个支付链路里最硬核的一段：

// pay/pay_apple.go：x5c[0]=叶证书，x5c[1]=中间证书，根是本地 Apple Root CA G3
opts := x509.VerifyOptions{
    Roots:         rootPool,    // AddCert(a.rootCACert)
    Intermediates: intermediatePool,
}
if _, err := leafCert.Verify(opts); err != nil {
    return nil, fmt.Errorf("certificate chain verification failed: %w", err)
}
// 再用叶证书公钥 ECDSA 验 JWS 签名（R||S 拼接格式，按曲线长度切开）

这里有个真实的运维细节：init() 加载不到 RootCAFile 时只是打一条 JWS signature verification will be DISABLED 的警告继续跑，代码里多处提醒「UNSAFE」——证书校验是可降级的，降级就等于裸奔，上线时必须配好 Apple Root CA G3。另外 Production 和 Sandbox 数据互相隔离，GetAppStoreOrder 先查主环境，404/401/403 就自动切另一环境重试，这样 TestFlight 测试者、App Review 审核、沙盒账号和正式用户都能被验证。

订阅：三层 JWS 通知与 originalTransactionId 映射

自动续订是另一条链路。苹果服务器通知 V2 的请求体是 {"signedPayload": "<JWS>"}，callback_subscribe_apple.go 要解三层：通知主体 → signedTransactionInfo → signedRenewalInfo，每层都过同一套 VerifyAndDecodeJWS。然后按通知类型分发：

// callback/callback_subscribe_apple.go
switch payload.NotificationType {
case "SUBSCRIBED":     // 首购：订单由App回调建，这里只同步订阅记录
    return handleSubscribedNotification(payload, txn, renewal)
case "DID_RENEW":      // 续订扣款成功：生成续费订单并发放会员权益
    return handleDidRenewNotification(payload, txn, renewal)
case "DID_FAIL_TO_RENEW":  // 计费重试/宽限期
case "EXPIRED", "GRACE_PERIOD_EXPIRED":  // 过期
case "REFUND", "REVOKE":  // 退款/撤销，只改状态并告警人工核查
}

关键映射是 originalTransactionId ↔ 用户：苹果后续的续订通知只带 originalTransactionId，没有这条记录就找不到人。所以支付成功的回调里会顺手 AppleSubscribe() 落一条 b_apple_subscription（在 callback_pay_apple.go 里直接调，注释说「不依赖 App 端再上报，App 上报还能兜底」）。续订成功时 DID_RENEW 先查 LatestTransactionId 和 FindPaidOrderByAppleTransaction 双幂等，再以苹果实际扣款（千分单位 price/10 转分）建一张 PayTypeAppleSubscribe 的成功订单发权益。价格管理侧，appstore/appstore_price.go 封装了对 App Store Connect API 的价格点读写：拉订阅/内购的 CHN 价格点、PushSubscriptionPrice 推送改价前必须先删掉已有 future price（Apple 规则：每个 territory 只能有一个未来价格），后台改价最终都沉淀到本地 LoadApplePrice(productId)，下单时优先用本地待生效价。

匿名购买：没登录也能先发货

iOS 用户可能没注册就先买了。order/anonymous_purchase.go 让这条路走得通：VerifyAnonymousPurchase 只凭 deviceId + appleOrderId + productId 就向苹果反查验证，产品 ID 对得上就落一条 b_anonymous_purchase（记下积分/会员权益快照，但不入账、不发权益）。等用户注册登录后，SyncAnonymousPurchasesToUser(deviceId, userId) 把未同步记录转成正常订单，再调公共的 HandleOrderResult(orderId, PayStatusSuccess, ...) 发放——两次事务：先建订单，再发权益并标记 is_synced。每条路径发放前同样过 FindPaidOrderByAppleTransaction，防止同一个交易被登录回调和匿名同步各发一次。

订单监控：内存统计 + 定时落库

order/order_monitor.go 不是对账兜底（它没有去拉微信/支付宝账单核对），而是一个订单活跃度计数器：UsageStatistics 用 datatype.AtomicU64 在内存里记当日/当月/总订单数，下单成功 dayAddOrder() +1，后台 goroutine 每 2 秒把变更写回 charge_statistics 配置表，跨天/跨月自动清零。注释里写得很诚实：「本统计方法只适合单机场景，如果是集群，需要改造」，且「只是粗略统计，允许有误差」。真正的对账兜底靠的是前面那套幂等闸门 + 各渠道 QueryOrderStatus 主动查询能力（注意支付宝和苹果的 QueryOrderStatus 目前还是 NotImplemented，线上目前只靠被动回调）。

权衡

  • 接口小而薄：Payer 只有三个方法，渠道特有的验签/查价留在各自包里，通过类型断言取出——换来的是下单主流程零分支，代价是回调 handler 仍要自己写胶水。
  • 幂等押注数据库：Redis 锁挂了也不重复发货，正确性由 WHERE pay_status=待支付 的条件更新保证——这是支付系统里最值钱的一条经验。
  • 苹果把校验做重：JWS 证书链 + BundleId + ProductId + 24 小时时效 + 交易级去重五道闸，因为 App 端回调天然不可信，一切以苹果服务器返回为准。
  • 匿名通道只存快照不发权益：把「验证」和「入账」解耦，既接住了未登录付费，又让幂等规则保持统一。

支付系统的复杂，从来不在「把钱收进来」，而在证明这笔钱真的属于这个用户、这个订单，且只发一次。三条渠道、五种支付方式、四条发放通道，最后收敛到同一个 Payer 接口和一句条件更新——这就是我们能睡着觉收钱的全部底气。
